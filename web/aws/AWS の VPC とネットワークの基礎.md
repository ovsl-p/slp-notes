# AWS の VPC とネットワークの基礎

## ひとことで

VPC はリージョン内に切った仮想ネットワークで、通信できるかどうかは「経路があるか（ルートテーブル）」と「フィルタで許可されているか（セキュリティグループとネットワーク ACL）」で決まる。

## なぜ効くか / どこで使うか

AWS の設計問題は、ほぼ全部ネットワークの上で起きる。サブネットの切り方、経路の通し方、外部から届くかどうかは、この基礎が分かっていないと判断できない。

コンテナや Kubernetes を使う場合も、EKS（標準の VPC CNI）では Pod に VPC の IP がそのまま振られるので、ここが曖昧だと Service や Ingress の話が呑み込めない。

## 前提となる知識

| 知っておくこと | なぜ必要か |
| --- | --- |
| IP アドレスと CIDR | VPC とサブネットは CIDR で切る。つなぐ相手と範囲が重複すると、経路でつなげない |
| ルーティング | 「どこ宛のパケットをどこへ送るか」の表。VPC の要 |
| NAT の考え方 | プライベートな IP のまま外に出る仕組み |
| DNS の基礎 | VPC の中にも名前解決の仕組みがある（[[AWS の DNS と名前解決]]） |

## 本体の解説

まず全体の形を1枚で。

![[assets/web/vpc-subnet-routing.svg]]

### 1. VPC とサブネット

VPC はリージョン内に1つ以上の CIDR ブロックで作る仮想ネットワークで、その中をサブネットで区切る。

サブネットは AZ に紐づく。1つのサブネットが複数の AZ にまたがることはないので、冗長化するなら AZ の数だけサブネットを作る。

パブリックとプライベートの違いは名前ではなく経路で決まる。サブネットのルートテーブルにインターネットゲートウェイへの経路があればパブリックで、なければプライベートになる。

### 2. ルートテーブル

ルートテーブルはサブネットに関連付ける。行は「宛先 CIDR」と「ターゲット（IGW、NAT ゲートウェイ、Transit Gateway、VPC ピアリングなど）」の組になる。

VPC 内の通信はローカルルートで自動的に通る。それ以外の宛先は、明示的に足さないと通らない。逆に言えば、足し忘れが「つながらない」の大半になる。

同じ VPC の中でも、サブネットごとに別のルートテーブルを当てられる。片方のサブネットだけ外部に出せる、という設計はここで作る。

### 3. 外に出るための装置

| 装置 | 役割 | 置き場所 |
| --- | --- | --- |
| インターネットゲートウェイ | パブリックサブネットと外部をつなぐ | VPC に1つ |
| NAT ゲートウェイ | プライベートサブネットから外へ出る（送信元 IP は NAT のものに変わる。外から内へは開始できない） | ゾーン型はパブリックサブネットに AZ ごと。リージョン型は VPC に1つ |
| VPC エンドポイント | AWS のサービスへ、インターネットを経由せずに届く | ゲートウェイ型はルートテーブル、インターフェイス型はサブネット内の ENI |

従来のゾーン型 NAT ゲートウェイは1つの AZ の中にしか存在しない。1つだけ置くと、その AZ が落ちたときに他の AZ からの通信も止まるので、AZ ごとに置いてルートテーブルも AZ ごとに分ける。

2025年11月からは、リージョン型（Regional NAT Gateway）も選べる。VPC に1つ作れば、ワークロードがある AZ に自動で広がるので、AZ ごとに作る手間とパブリックサブネットが要らなくなる。ただしプライベート NAT（インターネットに出ない NAT）には使えず、その用途はゾーン型のままになる。

VPC エンドポイントには2種類ある。ゲートウェイ型は S3 と DynamoDB 向けで、ルートテーブルに経路を足す形になる。インターフェイス型は ENI を作る形で、セキュリティグループが効く。PrivateLink はこのインターフェイス型の仕組みを使っている。

### 4. 通信を絞る2段

セキュリティグループはインスタンス（ENI）単位で、ステートフル（戻りの通信は自動で許可）で、許可ルールしか書けない。

ネットワーク ACL はサブネット単位で、ステートレス（戻りも明示的に許可する）で、拒否ルールも書ける。

実務では、細かい許可はセキュリティグループで行い、ネットワーク ACL は「この IP 範囲は丸ごと拒否」のような粗い制御に使う、という分担が多い。

ACL のルールは番号の小さい順に評価され、最初に一致したルールで許可か拒否が決まる。そのため、広い許可を小さい番号に置くと、後ろに書いた拒否は効かない。

### 5. DNS と VPC

VPC には、CIDR の先頭アドレスに +2 したアドレス（10.0.0.0/16 なら 10.0.0.2）に Route 53 Resolver がいる。+1 は VPC のルーター用で、DNS ではない。この Resolver は VPC の中からしか使えない。

詳細は [[AWS の DNS と名前解決]] に分けた。

### 6. 料金で効くところ

NAT ゲートウェイには、時間あたりの料金と、処理したデータ量あたりの料金がかかる。別の AZ にあるリソースとの通信にも、データ転送料金がかかる。

設計問題で「最もコスト効率よく」とあったら、まず NAT を通るデータを減らせないかを疑う（S3 や DynamoDB 宛てはゲートウェイ型エンドポイントに逃がす、など）。次に、AZ を跨ぐ通信を減らせないかを見る。

## 具体例・コード

最小の構成を頭の中で組み立てるときの順番。

1. VPC の CIDR を決める（例: 10.0.0.0/16）
2. AZ の数だけパブリックとプライベートのサブネットを切る（例: /24 ずつ）
3. パブリック側のルートテーブルに `0.0.0.0/0 → IGW` を入れる
4. プライベート側に `0.0.0.0/0 → NAT ゲートウェイ` を入れる（ゾーン型なら、同じ AZ の NAT を向ける）
5. セキュリティグループで、必要なポートだけ許可する

## つまずきポイント

- サブネットを「パブリックサブネット」という名前で作っただけで外部に出られると思う。決めているのはルートテーブル。
- ネットワーク ACL をステートフルだと思う。戻りの通信も明示的に許可しないと落ちる。
- ゾーン型の NAT ゲートウェイを1つだけ置いて冗長化したつもりになる。その AZ の障害で全体が止まる。
- CIDR が重複した VPC 同士をつなごうとする。ピアリングでも Transit Gateway でも、重複した範囲には経路を通せない。
- エンドポイントを「タダで速くなるもの」と思う。ゲートウェイ型は無料だが、インターフェイス型は AZ ごとの時間課金とデータ処理料金がかかる。
