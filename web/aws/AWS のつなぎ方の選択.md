# AWS のつなぎ方の選択

## ひとことで

つなぎ方は「誰と誰をつなぐか」と「経路を流すか、サービスだけ見せるか」の2軸で選ぶ。

## なぜ効くか / どこで使うか

VPC が増えるほど、経路の管理が破綻する。どの手段を選ぶかで、運用負荷・コスト・障害時の影響範囲が変わる。

設計問題でも実務でも、「とりあえずピアリング」で始めて、あとから全結合で手に負えなくなる、という流れがよく起きる。

## 前提となる知識

| 知っておくこと | なぜ必要か |
| --- | --- |
| ルーティングの基礎 | つなぐとは、経路を決めること |
| BGP の基礎 | 専用線と VPN は経路を交換して通す |
| 専用線とインターネット VPN の違い | 帯域・遅延・暗号化の前提が変わる |
| VPC の CIDR | 重複するとつなげない |

## 本体の解説

### 1. 2つの軸

1つ目の軸は、経路を流すか、サービスだけ見せるか。ピアリング・Transit Gateway・Direct Connect・VPN は経路を流す（L3）。PrivateLink と VPC Lattice は、相手のネットワークを見せずにサービスだけを公開する。

2つ目の軸は、1対1か、集約するか。VPC が2つならピアリングで足りる。増えるなら Transit Gateway でハブに集約する。

### 2. 経路を流す手段

| 手段 | 向く場面 | 注意 |
| --- | --- | --- |
| VPC ピアリング | VPC が少ない、1対1でよい | 推移的にならない。CIDR の重複不可 |
| Transit Gateway | VPC が多い、中央で集約したい | ルートテーブルでセグメント分離できる。アタッチメント単位の課金 |
| Site-to-Site VPN | インターネット経由で安くつなぐ | 帯域と遅延が不安定。トンネルは2本 |
| Direct Connect | 帯域と遅延を安定させたい | 専用線の契約が要る。単一経路だと冗長性がない |
| Cloud WAN | グローバルに拠点をつなぐ | ポリシーで一元管理する発想 |

Direct Connect は、どの経路を流すかで仮想インターフェイス（VIF）を選ぶ。プライベート VIF は VPC 向け、パブリック VIF は AWS のパブリックサービス向け、トランジット VIF は Transit Gateway 向けになる。

VPC と専用線をつなぐだけなら、プライベート VIF と仮想プライベートゲートウェイ（VGW）で足りる。VPC が増えて集約したくなったら Transit Gateway に替える。この違いは「VPC が1つか、複数か」で判断できる。

### 3. サービスだけ見せる手段

PrivateLink は、NLB の後ろにあるサービスを、VPC エンドポイント経由で公開する。相手の VPC とは CIDR が重複していてもよいのが大きな違いになる。

VPC Lattice は、サービス間の接続を L7 で扱う仕組みで、HTTP のルーティングや認証を中央でかけられる。

「CIDR が重複している」「相手に経路を見せたくない」「特定のサービスのみ公開したい」のどれかが出たら、PrivateLink 系を疑う。

### 4. セグメント分離

Transit Gateway では、ルートテーブルを分けて、どのアタッチメント同士を通信させるかを制御する。共有サービス VPC には全員から届かせ、部門の VPC 同士は互いに届かせない、という形が作れる。

セキュリティグループで止めるのではなく、経路として切るのが原則になる。経路で切っておけば、監査でも説明できる。

## 具体例・コード

判断の順番。

1. つなぐ相手は VPC か、オンプレか、外部のサービスか
2. 経路を流す必要があるか、サービスだけ見せれば足りるか
3. VPC の数は2つか、増えるか
4. CIDR は重複していないか
5. 帯域と遅延の要件は、インターネットで足りるか

## つまずきポイント

- ピアリングが推移的だと思う。A-B、B-C とつないでも A から C へは通らない。
- VPC が1つしかないのに Transit Gateway を選ぶ。構成が過剰になる。
- Direct Connect を引けば自動で冗長になると思う。経路も機器も二重化しないと止まる。
- CIDR が重複したままピアリングを計画する。あとから直すのは難しい。
- セキュリティグループで分離したつもりになる。VPC 間の分離は経路で切る。
