# AWS のつなぎ方の選択

## ひとことで

つなぎ方は「誰と誰をつなぐか」と「経路を流すか、サービスだけ見せるか」の2軸で選ぶ。

## なぜ効くか / どこで使うか

VPC が増えるほど、経路の管理が破綻する。どの手段を選ぶかで、運用負荷・コスト・障害時の影響範囲が変わる。

設計問題でも実務でも、「とりあえずピアリング」で始めて、あとから全結合で手に負えなくなる、という流れがよく起きる。

## 前提となる知識

| 知っておくこと | なぜ必要か |
| --- | --- |
| ルーティングの基礎 | つなぐとは、経路を決めること |
| BGP の基礎 | 専用線と VPN は経路を交換して通す |
| 専用線とインターネット VPN の違い | 帯域・遅延・暗号化の前提が変わる |
| VPC の CIDR | 重複するとつなげない |

## 本体の解説

判断の順番を1枚に。経路を流すか、サービスだけ見せるかで先に分かれる。

![[assets/web/aws-connectivity-choice.svg]]

### 1. 2つの軸

1つ目の軸は、経路を流すか、サービスだけ見せるか。ピアリング・Transit Gateway・Direct Connect・VPN は、お互いのネットワークに経路を通す（L3 でつなぐ）。PrivateLink と VPC Lattice は、相手にネットワーク全体は見せず、特定のサービスだけを公開する。

2つ目の軸は、1対1か、集約するか。VPC が2つならピアリングで足りる。増えるなら Transit Gateway でハブに集約する。

ここでよく出る「推移的」は、仲介を挟んでも関係が自動的に広がるかどうかという意味になる。A と B、B と C がつながっているとき、A と C も自動的につながるなら推移的。ピアリングはそうならないので非推移的、Transit Gateway はハブを経由して広がるので推移的になる。

経路を流すとは、相手の IP アドレス帯を自分のルートテーブルに足すことになる。A（10.0.0.0/16）から B（10.1.0.0/16）の DB に繋ぐなら、A のルートテーブルに `10.1.0.0/16 → pcx-...` の1行が増える。以降は A のどのインスタンスからも 10.1.x.x の全ポートに経路が通るので、絞るのはセキュリティグループの仕事になる。

サービスだけ見せる場合、その行は増えない。B の NLB をサービス化して A にエンドポイントを作ると、A のサブネットに ENI（例: 10.0.3.15）が1つ増えるだけになる。A のコードは 10.0.3.15:3306 に繋ぎ、10.1.0.0/16 は一度も出てこない。CIDR が重複していても成立するのはこのため。

ピアリングは「相手の VPC が自分の VPC の中に入る」のではなく、お互いの住所を自分の地図に書き込む関係になる。VPC の境界も、セキュリティグループも、課金も、IAM も別のまま残る。変わるのは「その宛先へ行く道がある」という点だけ。だから CIDR は組織全体で重複させない前提で先に設計する必要があり、あとから重複に気づくと VPC の作り直しになる。

ピアリングは3つ以上でも張れる。使えないのではなく、推移的でないために全結合になるのが難点になる。n 個の VPC で n(n-1)/2 本（3個なら3本、5個なら10本、10個なら45本）。本数と CIDR の重複チェックが人の手に負えなくなったら Transit Gateway に移す、というのが判断の目安になる。

### 2. 経路を流す手段

| 手段 | 向く場面 | 注意 |
| --- | --- | --- |
| VPC ピアリング | VPC が少ない、1対1でよい | 推移的にならない。CIDR の重複不可 |
| Transit Gateway | VPC が多い、中央で集約したい | ルートテーブルでセグメント分離できる。アタッチメントごとの時間課金とデータ処理料金がかかる |
| Site-to-Site VPN | インターネット経由で安く、すぐつなぐ | 帯域と遅延が不安定。1接続にトンネルが2本あり、両方使って冗長化する |
| Direct Connect | 帯域と遅延を安定させたい | 開通まで時間がかかる。暗号化はされないので、必要なら VPN や MACsec を重ねる。1回線だと冗長性がない |
| Cloud WAN | グローバルに拠点をつなぐ | ポリシーで一元管理する発想 |

Direct Connect は、どの経路を流すかで仮想インターフェイス（VIF）を選ぶ。プライベート VIF は VPC 向け、パブリック VIF は AWS のパブリックサービス向け、トランジット VIF は Transit Gateway 向けになる。

VPC が1つなら、プライベート VIF を仮想プライベートゲートウェイ（VGW）につなげば足りる。VPC が増えたら、Direct Connect ゲートウェイを挟んで複数の VGW に届かせるか、トランジット VIF で Transit Gateway につないで集約する。VPC 同士も通信させたいなら Transit Gateway を選ぶ。

### 3. サービスだけ見せる手段

PrivateLink の基本形では、提供側が NLB の後ろにサービスを置いてエンドポイントサービスにし、利用側は自分の VPC にインターフェイス型の VPC エンドポイントを作ってそこへ接続する。経路をつなぐわけではないので、お互いの CIDR が重複していてもよい。ここが経路を流す手段との大きな違いになる。

VPC Lattice は、サービス間の接続を主に L7（HTTP や gRPC）で扱う仕組みで、パスによる振り分けや IAM による認証をまとめてかけられる。

「CIDR が重複している」「相手に経路を見せたくない」「特定のサービスのみ公開したい」のどれかが出たら、PrivateLink 系を疑う。

### 4. セグメント分離

Transit Gateway では、ルートテーブルを分けて、どのアタッチメント同士を通信させるかを制御する。共有サービス VPC には全員から届かせ、部門の VPC 同士は互いに届かせない、という形が作れる。

セキュリティグループで止めるのではなく、経路として切るのが原則になる。経路で切っておけば、監査でも説明できる。

## 具体例・コード

判断の順番。

1. つなぐ相手は VPC か、オンプレか、外部のサービスか
2. 経路を流す必要があるか、サービスだけ見せれば足りるか
3. VPC の数は2つか、増えるか
4. CIDR は重複していないか
5. 帯域と遅延の要件は、インターネットで足りるか

## つまずきポイント

- ピアリングが推移的だと思う。A-B、B-C とつないでも A から C へは通らない。
- VPC が1つしかないのに Transit Gateway を選ぶ。構成が過剰になる。
- Direct Connect を引けば自動で冗長になると思う。回線もロケーションも二重化しないと、1か所の障害で止まる（安く済ませるなら VPN をバックアップにする）。
- Direct Connect なら暗号化されていると思う。専用線でも暗号化はされない。
- CIDR が重複したままピアリングを計画する。あとから直すのは難しい。
- セキュリティグループだけで分離したつもりになる。VPC 間の分離は、まず経路で切る。
