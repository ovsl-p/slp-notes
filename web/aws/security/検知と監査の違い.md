# 検知と監査の違い

## ひとことで

検知と監査のサービスは、記録するもの、設定を評価するもの、攻撃らしい動きを見つけるものに分かれる。どれも止めはしない。

## なぜ効くか / どこで使うか

調べたいことを先に決めると、使うサービスが決まる。誰が API を呼んだかを追いたいなら CloudTrail、設定が社内基準から外れていないかを見たいなら Config、不正な侵入の兆候を見つけたいなら GuardDuty を使う。

やりたいことが動詞（記録する、評価する、検知する、集約する）で言えると選びやすい。逆に、止める、拒否することが目的なら、このノートのサービスでは足りない。権限なら SCP や IAM、通信なら WAF やセキュリティグループで止める（[[通信とアプリの防御]]）。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| API | AWS への操作はすべて API 呼び出しとして行われる。コンソールも CLI も裏側は同じ。 |
| 証跡（ログ） | API 呼び出しや通信などの起きたことの記録。あとから追うために残す。 |
| 設定 | リソースの状態（暗号化の有無、公開の範囲など）。今どうなっているかを表す。 |
| 脆弱性 | ソフトウェアやイメージに含まれる既知の弱点。修正版の有無が対応を分ける。 |
| 検知と記録 | 検知は攻撃らしい動きを見つけること、記録はあとから追えるように残すこと。 |

## 本体の解説

### 1. 追うもので分ける

| どの問い | サービス | 役割 |
|---|---|---|
| 誰が何をしたか | CloudTrail | API の操作履歴を残す |
| 設定が基準に合うか | Config | 設定の変更を記録し、ルールと照らして評価する |
| 攻撃らしい動きか | GuardDuty | 継続的に監視して悪意のある活動を検知する |
| 検出結果を集約し、リスクを優先 | Security Hub | 各サービスの検出結果を関連付けて露出を計算する |
| 基準への適合をチェック | Security Hub CSPM | セキュリティ基準ごとに設定を評価する |
| S3 の中の機密 | Macie | S3 の中の個人情報などの機密データを見つける |
| ソフトの穴 | Inspector | EC2、コンテナイメージ、Lambda 関数の脆弱性を検査する |

### 2. CloudTrail（API の操作記録）

CloudTrail は、ユーザー、ロール、AWS サービスが行った操作（API 呼び出し）を記録する。監査の証跡として使うのが基本の役割になる。記録するだけで、攻撃を止めることはしない。

既定で残るのは、リソースの作成や設定変更といった管理イベントだけになる。S3 のオブジェクト操作や Lambda の実行といったデータイベントは、証跡やイベントデータストアで有効にしないと記録されない。組織の証跡を設定すると、組織内の全アカウントのログを一か所に集められる。ここでは記録の仕組みだけを扱い、組織全体の設計は [[組織の統制サービスの違い]] と [[マルチアカウントのガバナンス]] に任せる。

### 3. Config（設定の履歴と評価）

Config は、AWS リソースの設定を記録し、設定の変更履歴を残す。さらにルール（基準）と照らして準拠しているかを評価する。ルールを束ねた適合パック（conformance pack）を使えば、まとめて適用できる。Config は設定を止めるのではなく、基準から外れていることを検出して報告する。

### 4. GuardDuty（脅威の検知）

GuardDuty は、継続的に監視して悪意のある活動を検知する。入力には CloudTrail のログ、VPC フローログ、DNS ログなどを使う。機械学習と脅威インテリジェンスを組み合わせて判断する。検知するのが役割であり、自動で遮断はしない。遮断は別の仕組みで行う。

### 5. Security Hub（検出結果の集約）と Security Hub CSPM（基準のチェック）

2025年12月に新しい Security Hub が一般提供になり、それまでの Security Hub は Security Hub CSPM という名前に変わった。役割は2つに分かれる。

Security Hub は、GuardDuty、Inspector、Macie、Security Hub CSPM の検出結果（findings）を集めて関連付け、複数の問題が重なって生まれる露出（exposure）を計算する。Security Hub CSPM は、セキュリティ基準ごとに設定をチェックし、不備を検出する。2つは別々に有効にする。Security Hub CSPM を有効にしていないと、Security Hub は CSPM の検出結果を露出の計算に使えない。AWS は両方を有効にすることを勧めている。

資料の版によって、旧名の Security Hub が基準のチェックの意味で書かれていることがある。集約と優先度の話か、基準の適合の話かで読み分ける。

### 6. Macie（S3 の機密データの発見）と Inspector（脆弱性検査）

Macie は、S3 の中の機密データ（個人情報など）を機械学習とパターンマッチングで見つける。公開されたバケットや暗号化されていないバケットがあれば知らせる。対象は S3 に限られる。

Inspector は、EC2、コンテナイメージ（ECR）、Lambda 関数のソフトウェアの脆弱性を継続的に検査する。ネットワークの公開範囲の検査も行う。Macie がデータの中身を見るのに対し、Inspector はソフトの穴を見る。

Detective は、検知結果を調べて原因を追うためのサービスである。このノートでは名前だけを述べ、詳細は扱わない。

## 具体例・コード

不審なログインがあったときの流れで、各サービスの役割を見る。

1. 誰かが通常と違う操作を行うと、その操作は CloudTrail に API 呼び出しとして記録される。CloudTrail は誰が、いつ、何をしたかを残すだけで、そのログインを止めることはしない
2. GuardDuty は、CloudTrail などのログを継続的に分析し、通常と違う挙動を悪意のある活動の兆候として検知し、findings を出す。遮断は行わない
3. Security Hub は、GuardDuty の findings を他のサービスの結果と一緒に集め、優先度を付けて一画面に表示する。調べる順番を決める材料になる
4. 次に Config で、そのユーザーが触ったリソースの設定が基準に合っているかを確認する。設定が基準から外れていれば、Config が報告する
5. S3 の中のデータが対象になっていた場合は Macie、ソフトの穴が疑われる場合は Inspector が、それぞれ別の観点から確認に使われる

S3 のオブジェクトを誰が読んだかを追うには、CloudTrail のデータイベントを有効にしておく。既定では管理イベントしか残らない。

## つまずきポイント

- 「CloudTrail を入れれば攻撃が防げる」は間違い。記録するだけで、攻撃を止めない。記録は事後の追跡に使う。
- 「GuardDuty を入れれば設定の不備も見つかる」は間違い。GuardDuty が見つけるのは攻撃らしい動き（脅威）で、設定の評価は Config が担う。
- 「Security Hub が脅威を見つける」は間違い。脅威を見つけるのは GuardDuty、基準のチェックは Security Hub CSPM。Security Hub は集約と露出の計算を担う。
- 「Macie と Inspector は同じものだ」は間違い。Macie は S3 の中の機密データを、Inspector はソフトウェアやイメージの脆弱性を見る。対象も目的も違う。
- 「検知と記録は予防と同じだ」は間違い。このノートのサービスは検知と記録を担う。止めるのは、権限なら SCP や IAM、通信なら WAF やセキュリティグループ。
- 「CloudTrail を有効にすれば S3 のオブジェクトを誰が読んだかも残る」は間違い。既定で残るのは管理イベントだけ。データイベントは有効にして初めて記録される。
