# IAM と権限の仕組み

## ひとことで

誰が・何を・どのリソースにできるかをポリシーで書き、明示的な拒否が最優先で、書き忘れは全部拒否になる。

## なぜ効くか / どこで使うか

403 が出たとき、S3 が読めないとき、別アカウントから届かないとき、原因は評価の順番のどこかにあることが多い。SCP や RCP も、この評価の中で働く層のひとつになる。

順番を知っていれば、どの層で止まっているかを切り分けられ、足す場所を間違えない。権限を足すより「なぜ足りないのか」を説明できるほうが、実務では強い。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| 認証と認可 | 「誰か」を決めるのが認証、「何をしてよいか」が認可。IAM は後者。 |
| プリンシパル | 操作する側。ユーザー、ロール、AWS のサービス。 |
| JSON | ポリシーは JSON。Effect、Action、Resource の3つが骨格。 |
| 一時認証情報 | 期限つきの鍵。ロールを使うとこれが手に入る。 |

## 本体の解説

![[assets/web/aws-iam-evaluation.svg]]

### 1. 3つの登場人物

操作する側をプリンシパル、操作される側をリソース、その間を決めるのがポリシーだ。

ポリシーは2種類ある。プリンシパルに貼るものをアイデンティティベース、リソースに貼るものをリソースベースと呼ぶ。S3 のバケットポリシーや KMS のキーポリシーが後者にあたる。

リソースベースのポリシーだけが `Principal` を書ける。誰に許すかをリソース側から指定できるのは、こちらだけだ。

### 2. 評価の順番

判定は次の順になる。

1. どこかに明示的な拒否（`Deny`）があれば、その時点で拒否
2. 上限（SCP、RCP、権限の境界、セッションポリシー）のすべての中で許可されていて、かつアイデンティティかリソースのポリシーで許可されていれば許可。同じアカウント内なら片方で足り、別アカウントは §5 の両側ルールになる
3. どれかで許可が無ければ拒否（暗黙の拒否）

許可は足し算で決まり、上限はすべてを満たした範囲だけが残る。上限の中に Allow が無ければ、アイデンティティ側で許可していても止まる。

止まり方は上限の種類で変わる。SCP は、既定の FullAWSAccess に `Deny` を足す拒否リスト型で運用することが多く、その場合は明示的な拒否で止まる。許可リスト型にすれば暗黙の拒否になる。権限の境界とセッションポリシーは、Allow が無ければ暗黙の拒否で止まる。

だから「許可を足したのに効かない」ときは、明示的な拒否を先に探し、次に上限のどこで許可されていないかを見る。組織の SCP、バケットポリシーの拒否、KMS のキーポリシー、境界のどれかが効いている。

### 3. ロールと AssumeRole

ロールは「権限の束」で、人にもサービスにも、別アカウントにも貸せる。

引き受けるときは STS の `AssumeRole` を呼ぶ。返ってくるのは期限つきの一時認証情報で、IAM ユーザーのアクセスキーのような長期の鍵ではない。

ロールには信頼ポリシーがある。「誰がこのロールを引き受けられるか」を書く場所で、権限を書くポリシーとは別物になる。ここを間違えると、権限は足りているのに AssumeRole が拒否される。

人の代わりに動く処理（CI、Lambda、EC2）は、原則ロールにする。鍵を配らずに済むのが最大の利点だ。

### 4. 上限をかける4つ

許可を絞る道具は、貼る場所が違う。

| 道具 | 何を縛るか | 誰が設定するか |
|---|---|---|
| SCP | アカウント内のプリンシパルの操作 | 組織の管理者 |
| RCP | アカウント内のリソースへの操作 | 組織の管理者 |
| 権限の境界 | 1つのユーザーやロールの最大権限 | アカウントの管理者 |
| セッションポリシー | 引き受けたセッションの最大権限 | 引き受ける側 |

SCP、RCP、権限の境界、セッションポリシーはどれも、許可はせず上限を下げるだけで共通している。

境界がどこまで効くかは、リソースベースのポリシーが誰に許可したかで変わる。同じアカウント内で IAM ユーザーやロールセッションの ARN に直接許可した場合は、境界で止まらない。IAM ロールの ARN に許可した場合は、境界の暗黙の拒否で止まる。クロスアカウントのアクセスは呼び出し元の評価になるので、境界はそちら側にかかる。

SCP が組織の外からのリソースベースの許可を止められないのは、SCP が効くのがそのアカウントのプリンシパルだけだからである。リソース側から上限をかけるのが RCP（resource control policy）で、そのアカウントのリソースへの操作に、呼び出し元がどこにいても上限をかける。同じアカウントのプリンシパルからの操作にも効くが、管理アカウントのリソース、サービスリンクロール、AWS マネージドの KMS キーは対象外になる。かかるのは、S3、STS、KMS、SQS、Secrets Manager など対応しているサービスだけになる。

### 5. クロスアカウントの2方向ルール

アカウントをまたぐときは、両側で許可が要る。

呼び出し元のアイデンティティに「このリソースを触ってよい」と書き、リソース側にも「このプリンシパルに許す」と書く。片方だけでは通らない。

ロールを引き受ける形なら、A 側で `sts:AssumeRole` を許可し、B 側の信頼ポリシーで A を信頼する。この2枚が揃って初めて鍵が返る。

SCP は、その SCP が付いたアカウントのプリンシパル（IAM ユーザー、ロール、ルートユーザー）に効く。管理アカウントのプリンシパルには効かない。

B のバケットポリシーで A を許可している形では、効くのは A の SCP だけになる。B 側の SCP は、呼び出し元が B のプリンシパルではないので関与しない。B の組織で外からのアクセスを止めたいなら、RCP か `aws:PrincipalOrgID` の条件を使う。

B のロールを `AssumeRole` する形なら話が変わる。引き受けたセッションは B のプリンシパルになるので、そこで B の SCP も効く。

### 6. 条件キー

ポリシーには条件を書ける。実務で一番効くのは条件だ。

`aws:SourceIp` で接続元を絞る、`aws:PrincipalOrgID` で組織内だけに許す、`aws:MultiFactorAuthPresent` で MFA を要求する、`aws:RequestedRegion` で使えるリージョンを絞る、といった形で使う。

`aws:PrincipalOrgID` は、組織の外のアカウントからリソースベースのポリシー経由で来るアクセスを止める数少ない手段になる。SCP が効かない場面を、条件で埋める形になる。

### 7. 人が入る経路

人が複数アカウントに入るときは、IAM ユーザーを作らずに IAM Identity Center を使う。外部の IdP と連携して、権限セットをアカウントに割り当てる。

ロールと IdP によるサインインにすれば、キーを配る運用をやめられる。退職や異動のときは IdP 側を止めるだけで、新しいサインインを止められる。すでに引き受けたロールセッションは期限（最大12時間）まで残るので、即座に止めたいときは、そのユーザーの ID を条件にした `Deny` を SCP に入れる。

## 具体例・コード

別アカウント B の S3 バケットを、アカウント A の Lambda から読む場合を、4つの手順で組む。

1. B のバケットポリシーに、A の Lambda 用ロールを `Principal` として `s3:GetObject` を許可する
2. A の Lambda のロールに、そのバケットへの `s3:GetObject` を許可する
3. バケットが KMS で暗号化されているなら、キーポリシーで A のロールに `kms:Decrypt` を許可し、A のロールの IAM ポリシーにも `kms:Decrypt` を足す。キーはカスタマーマネージドキーを使う。`aws/s3` などの AWS マネージドキーはキーポリシーを変えられないので、クロスアカウントでは使えない。この2枚を書く代わりに、鍵の所有者が A のロールへグラントを発行する手もある（[[暗号化と秘密情報の管理]]）
4. A の SCP で S3 が禁止されていないことを確認する。B 側で外からのアクセスを絞りたいなら、RCP も見る

どこか1つ欠けると 403 になる。403 が出たら、欠けているものを順に潰す。3の KMS では、キーポリシーと IAM ポリシーの2枚が要るので、片方だけ直して終わりにしない。

## つまずきポイント

- 「リソースベースのポリシーを書けば、呼び出し元の許可は要らない」は間違い。別アカウントでは両方要る。
- 「S3 の許可が揃っていれば読める」は間違い。バケットが KMS で暗号化されていると、キーポリシーか自分の IAM ポリシーのどちらかが欠けているだけで読めない。
- 「境界は、リソースベースの許可に対する万能のブレーキだ」は間違い。止まるのは同じアカウント内でロールの ARN に許可した場合で、IAM ユーザーやロールセッションの ARN への許可は通る。
- 「SCP で何かを許可できる」は間違い。SCP は上限を下げるだけで、許可はしない。
- 「アクセスキーを発行して配ればよい」は間違い。ロールで足りる場面が多く、鍵は漏れる前提で扱うものになる。
- 「拒否が効いていても、許可を足せば直る」は間違い。`Deny` は許可より先に評価されるので、まず `Deny` を探す。
