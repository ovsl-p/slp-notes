# 認証と認可の入口

## ひとことで

誰がどこから入ってくるか（人、アプリ、利用者）によって入口を分け、入った後の許可は IAM の評価で決まる。

## なぜ効くか / どこで使うか

AWS の認証を設計するときは、どのユーザーを、どの仕組みで認証し、どの権限を与えるかを決める。入口を間違えると、権限をいくら絞っても、そもそも漏れる経路が残る。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| 認証（authentication） | 相手が誰かを確かめる。 |
| 認可（authorization） | 確かめた相手に、何をしてよいかを決める。 |
| 一時認証情報 | ロールを引き受けると手に入る期限つきの鍵。長期のアクセスキーは、漏れると長く使われるので避ける。 |
| MFA | パスワードに加えて、2つ目の要素で確かめる。 |

## 本体の解説

### 1. 入ってくる相手で分ける

| 相手 | 入口 | 役割 |
|---|---|---|
| 社員や運用者（人が AWS に入る） | IAM Identity Center | 複数アカウントへのシングルサインオンを提供する |
| EC2、Lambda など（アプリが AWS に入る） | IAM ロール | 一時認証情報の自動受け取りを提供する |
| 外部の利用者（自社アプリを使う人） | Cognito | サインアップ、サインイン、ソーシャルログインを提供する |
| 社内の Windows 環境（AD に依存） | Directory Service | 既存の Active Directory を使う環境を提供する |

### 2. IAM Identity Center（人の入口）

社員の ID は、外部の IdP（例: 社内の認証基盤）に持たせて、Identity Center と SAML や SCIM で連携する。そして、権限セットを決めて、各アカウントに割り当てる。割り当てると、アカウントに対応するロールが作られて、利用者はそのロールを一時認証情報で引き受ける。

IAM ユーザーをアカウントごとに作る運用は、退職や異動のときに消し忘れが起きやすい。入口を Identity Center に寄せれば、IdP で止めるだけで新しいサインインは全アカウントで止まる。

ただし、すでに引き受けたロールセッションは期限（最大12時間）まで残る。即座に止めるには、そのユーザーの ID を条件にした Deny を SCP に入れる。Identity Center の Access portal のセッションを削除しても、引き受け済みのロールセッションは止まらない。

### 3. Cognito（アプリの利用者の入口）

Cognito は2つの役割を分けて扱う。

- ユーザープール: 利用者の登録と認証を担う。成功すると、アプリが使うトークン（JWT）を返す
- アイデンティティプール: 認証された利用者に、AWS の一時認証情報を渡す。スマホアプリの利用者が、自分専用の S3 のフォルダにだけ直接アクセスする、といった場面で使う

### 4. Directory Service（AD に依存する環境）

Active Directory に依存する Windows の環境や、AD 認証の RDS などで使う。

- AWS Managed Microsoft AD: AWS の中に本格的な AD を作る。オンプレの AD と信頼関係を結べる
- AD Connector: オンプレの AD への中継。AD の情報は AWS にコピーしない
- Simple AD: 小規模向けの簡易な AD。信頼関係は結べない

オンプレの AD の情報を AWS に複製したくないなら AD Connector、AWS の中で AD を使いたいなら Managed Microsoft AD、と分けて考える。

### 5. フェデレーション（外部の ID を使う）

フェデレーションは、AWS 固有のサービス名ではなく、一般的な単語。複数の組織や仕組みが、互いの認証を信頼して連携する考え方を指す。AWS では、外部の ID 基盤で確かめた人を、IAM のロールに結び付ける形で使う。

仕組みとしては、SAML 2.0 か OIDC で外部の認証結果を受け取り、IAM のロールを引き受けて一時認証情報を得る。長期のアクセスキーを配らずに済むので、人にもアプリにも基本はこの形にする。

IAM の SAML フェデレーションは、アカウントごとに SAML プロバイダーとロールを作る。複数アカウントに同じ権限を配るなら、手作業が増える。その管理を一か所にまとめたものが、IAM Identity Center になる。

### 6. 認可は IAM の評価で決まる

入口で認証されたあと、何を許すかは [[IAM と権限の仕組み]] で書いた評価の順番で決まる。ロールの権限ポリシー、リソースのポリシー、境界、SCP のどれかが拒否すれば、認証が通っても止まる。

## 具体例・コード

社内の開発者が、本番の AWS にアクセスする流れ。

1. 開発者は、社内の認証基盤（IdP）でサインインする（MFA 込み）
2. Identity Center が、IdP の情報をもとに、その人の権限セットを確かめる
3. 本番アカウントに対応するロールを、一時認証情報で引き受ける
4. 権限の上限は、組織の SCP と、ロールの権限で決まる
5. 退職したら、IdP のアカウントを止める。新しいサインインは止まるが、引き受け済みのロールセッションは期限（最大12時間）まで残る。即座に止めるなら、ユーザー ID を条件にした Deny を SCP に入れる

## つまずきポイント

- 「Cognito のユーザープールは、AWS の S3 に直接アクセスさせる仕組みだ」は間違い。ユーザープールは登録と認証を担う。直接アクセスはアイデンティティプールの役割。
- 「Identity Center の権限セットは、そのまま IAM ユーザーだ」は間違い。割り当てると、アカウントのロールが作られる。
- 「Simple AD はオンプレの AD と信頼関係を結ぶ用途に使える」は間違い。Simple AD は信頼を結べない。そういうときは Managed Microsoft AD か AD Connector を使う。
- 「認証が通れば、権限は全部使える」は間違い。認可の評価で、SCP や境界が止めることがある。
- 「アプリに長期のアクセスキーを埋め込めばよい」は間違い。漏れると長く使われるので、ロールを使う。
- 「Access portal のセッションを削除すれば、退職者のアクセスは即座に止まる」は間違い。引き受け済みのロールセッションは期限まで残る。即座に止めるには、ユーザー ID を条件にした Deny を SCP に入れる。
