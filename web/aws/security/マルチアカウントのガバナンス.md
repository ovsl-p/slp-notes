# マルチアカウントのガバナンス

## ひとことで

アカウントを分けて境界を作り、その上に許可の上限と監査を重ねて、AWS のガバナンスを組む。

## なぜ効くか / どこで使うか

1つのアカウントに全部載せると、権限も請求も障害範囲も混ざる。分けると、今度は誰が何をできるかを全体で揃える必要が出てくる。

SCP、Control Tower、IAM Identity Center は、この統制を揃える役を担う。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| IAM | 誰に何を許可するかを決める。 |
| AssumeRole | 別アカウントのロールの権限を一時的に借りる。 |
| OU | アカウントをまとめ、ポリシーを下の階層へ継承させる単位。 |
| 請求の分離 | アカウントごとに費用を分けて見る。 |

## 本体の解説

境界はアカウントで作り、統制は OU の継承で揃える。

![[assets/web/aws-multi-account.svg]]

### 1. アカウントを分ける理由

分ける理由は主に4つある。権限の境界を作る、障害や事故の影響範囲を閉じ込める、請求を部署やシステムごとに分ける、規制や監査の対象範囲を区切る、である。

分けたあとも、共通のログ置き場やネットワークは全アカウントで揃えたい。そのためにガバナンスの道具が要る。

### 2. Organizations と SCP

Organizations でアカウントを束ね、OU（組織単位）で階層を作る。

SCP（サービスコントロールポリシー）は、メンバーアカウントの IAM ユーザーとロール（ルートユーザーも含む）ができる操作の上限を決める。SCP 自体は何も許可しない。実際に使える権限は、IAM で許可され、かつ SCP でも上限内にあるものだけになる。

効かない範囲もある。管理アカウントには適用されず、サービスリンクロールにも効かない。また、SCP が縛るのは自分の組織のプリンシパルだけなので、組織外のアカウントがリソースベースのポリシー（S3 のバケットポリシーなど）で許可されてアクセスしてくる場合は止められない。リソース側から上限をかけるのは、リソースコントロールポリシー（RCP）が担う。

### 3. Control Tower

Control Tower は、マルチアカウントの初期構成（Landing Zone）を作り、各アカウントが決めたルールに沿った状態を維持する。

ルール（コントロール。以前はガードレールと呼んでいた）には3種類ある。違反する操作をそもそも止める予防的コントロール（SCP や RCP で実装）、違反を見つけて知らせる検出的コントロール（AWS Config で実装）、リソースを作る前に CloudFormation のテンプレートを検査するプロアクティブコントロールだ。アカウントの発行は Account Factory で行い、作るたびに同じ設定が当たる。

Control Tower は、新しいアカウントを同じ設定で量産したいときや、設定の逸脱を検出したいときに使う。

### 4. IAM Identity Center

人が複数アカウントに入るときの入口になる。外部の IdP と連携し、権限セットをアカウントに割り当てる。

IAM ユーザーをアカウントごとに作る運用は、人の異動や退職で破綻する。Identity Center に寄せておけば、IdP 側でユーザーを無効にするだけで、全アカウントへのアクセスがまとめて止まる。

### 5. 監査と共有

ログや検出結果は中央のアカウントに集める。CloudTrail の組織トレイル、Config のアグリゲータ、GuardDuty の委任管理者が定番の手段だ。

リソースの共有は RAM を使う。VPC サブネット、Transit Gateway、Resolver のルール、ライセンスなどを、アカウントをまたいで共有できる。

## 具体例・コード

新しいアカウントを1つ足すときの流れ。

1. OU を決める（本番、検証、サンドボックスなど）
2. Control Tower の Account Factory でアカウントを作る
3. その OU に継承される SCP を確認する
4. Identity Center で、必要な人のグループに権限セットを割り当てる
5. ログの集約先に、そのアカウントの証跡が届くことを確認する

## つまずきポイント

- 「SCP で何かを許可できる」は間違い。SCP は上限を下げるだけで、許可はしない。
- 「管理アカウントにも SCP が効く」は間違い。管理アカウントには効かない。
- 「SCP で、組織外からリソースベースのポリシー経由で来るアクセスを止められる」は間違い。止められないので、リソース側から上限をかける RCP を使う。
- 「IAM ユーザーをアカウントごとに作り続ける運用で足りる」は間違い。退職時に無効化の漏れが起きるので、Identity Center に寄せる。
- 「ログを各アカウントに置いたままで監査になる」は間違い。改ざんや削除ができてしまうので、中央のアカウントに集める。
