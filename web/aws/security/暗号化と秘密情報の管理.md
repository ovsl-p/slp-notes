# 暗号化と秘密情報の管理

## ひとことで

データは鍵で守り、鍵は誰が管理するかと置き場所で選ぶ。秘密情報は暗号化して保管し、入れ替えは自動に任せる。

## なぜ効くか / どこで使うか

鍵とパスワードの扱いが甘いと、暗号化しても守れない。鍵の作成、利用の許可、入れ替え、削除を誰が担うか決めておくと、漏えいしたときの影響範囲を絞れ、監査でも説明できる。

使う場面は、業務データベースの暗号化、アプリの接続パスワードの管理、Web の証明書の運用、S3 の保管設計である。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| 保存時の暗号化 | ディスクやバケットに置いたデータを、鍵で暗号化すること。 |
| 通信時の暗号化 | TLS で、経路上のデータを暗号化すること。 |
| 鍵の管理 | 鍵を作る、使わせる、入れ替える、消す。この4つを誰が担うかが論点。 |
| エンベロープ暗号化 | データをデータキーで暗号化し、そのデータキーをマスターキーで包む二段構え。 |
| HSM | 鍵を守る専用のハードウェアセキュリティモジュール。 |

## 本体の解説

### 1. 管理の主体で選ぶ

| 欲しいもの | サービス | 特徴 |
|---|---|---|
| 鍵を AWS の仕組みで安全に管理したい | KMS | 暗号鍵を作り、使用を IAM とキーポリシーで制御する |
| 鍵を自分だけが占有したい、専用の HSM が要る | CloudHSM | 専用のハードウェアで、鍵を利用者の管理下に置く |
| パスワードや API キーを保管して、定期的に入れ替えたい | Secrets Manager | 秘密情報の保管と、自動ローテーション |
| 設定値や軽い秘密情報を保管したい | パラメータストア | 安く手軽。SecureString は KMS で暗号化する |
| 通信の TLS 証明書を使いたい | ACM | 証明書の発行と、自動更新 |

### 2. エンベロープ暗号化

データはデータキーで暗号化し、そのデータキーをマスターキーで包む。データ本体はデータキーで処理するので、大きなデータも速く扱え、マスターキーは外に出ない。

EBS や RDS の暗号化、S3 の SSE-KMS は、内部で KMS が発行したデータキーを使ってデータを暗号化する。S3 の既定の暗号化（SSE-S3）は KMS を使わない。

### 3. KMS の鍵と許可

KMS は、鍵素材を種類を問わず外に出さない。非対称鍵でも、ダウンロードできるのは公開鍵だけだ。

鍵の種類は、AWS マネージドキーとカスタマーマネージドキーの2つ。カスタマーマネージドキーは、キーポリシーで使える人を決め、ローテーションの設定、無効化、削除の待機期間も自分で決める。

許可の入口はキーポリシーだ。同じアカウントでの扱いは次のとおり。

- キーポリシーがプリンシパルを直接許可する場合、IAM ポリシーは不要
- キーポリシーがアカウントに委任している場合、IAM ポリシーだけで足りる

別アカウントから使うときは、キーポリシーで相手アカウントを許し、呼び出し側の IAM でも許可する。IAM 側の仕組みは [[IAM と権限の仕組み]] にある。

### 4. AWS マネージドキーとカスタマーマネージドキーの選び方

AWS マネージドキーは、ポリシーもローテーションも AWS が決める。月額はかからず、手間もない。ただし、その鍵への API リクエストには料金がかかる。カスタマーマネージドキーには、鍵ごとの月額と API 呼び出しの料金がかかる。共有や監査の要件がなければ、AWS マネージドキーで足りることが多い。

カスタマーマネージドキーを選ぶのは、次の条件に当てはまるときだ。

- 別のアカウントと暗号化したデータを共有したい。相手をキーポリシーで許可できるのは、この鍵だけ
- 監査や規制で、鍵を使える人をキーポリシーで示す必要がある
- 鍵の入れ替えを自分の周期で行いたい、または自動ローテーションを止めたい
- 鍵を無効化して、データを読めなくする緊急停止をしたい
- 独自の鍵素材を持ち込む（BYOK）、またはカスタムキーストアで CloudHSM を使いたい

### 5. CloudHSM（専用の HSM）

CloudHSM は、専用の HSM を VPC の中に置く。鍵の作成と利用は、利用者が管理する HSM ユーザーが行う。AWS の運用者も鍵の中身は見られない。

KMS も CloudHSM も、使う HSM は FIPS 140-3 のレベル3 の認定を受けている。FIPS のレベルでは両者を分けられない。CloudHSM を選ぶのは、次のときだ。

- HSM を単一のテナントで占有したい
- 鍵を AWS の API ではなく、PKCS#11 などで直接扱いたい

### 6. Secrets Manager とパラメータストア

Secrets Manager は、データベースのパスワードや API キーを保管する。アプリは API で取り出すので、ソースにパスワードを書かずに済む。最大の特徴は自動ローテーションだ。RDS などでは、Secrets Manager がパスワードを定期的に変え、アプリは変更を意識せず使い続けられる。料金は秘密情報の数と、API の呼び出し回数で決まる。

パラメータストアも秘密情報を保管でき、SecureString は KMS で暗号化される。ただし標準では自動ローテーションがない。定期的な入れ替えが要るなら Secrets Manager、設定値を安く保管するならパラメータストアを選ぶ。

### 7. ACM（証明書）

ACM は TLS 証明書を発行し、ELB、CloudFront、API Gateway で使う。ACM が発行した公開証明書は、更新も自動で行われる。

ACM が発行した公開証明書は秘密鍵を取り出せないので、ACM と連携するサービスに関連付けて使う。EC2 に直接入れたいときの選択肢は次のとおり。

- エクスポート可能として発行したパブリック証明書（有料、発行時に指定）
- ACM プライベート CA
- 外部の証明書

### 8. S3 の暗号化と通信

S3 の保存時の暗号化は、次の3つから選ぶ。

- SSE-S3: AWS が鍵を管理する
- SSE-KMS: KMS の鍵を使う
- SSE-C: 利用者が鍵を渡す

通信は TLS で守る。バケットポリシーで `aws:SecureTransport` の条件を使うと、暗号化されていない通信を拒否できる。S3 全体の違いは [[ストレージサービスの違い]] にある。

## 具体例・コード

社内の業務データベースを守る構成を、4つの手順で組む。

1. 業務データベースは、カスタマーマネージドの KMS キーで暗号化する
2. 接続パスワードは Secrets Manager に置き、30日ごとに自動で更新する
3. 外部に公開する Web の証明書は ACM で発行し、ロードバランサに付ける
4. 規制で専用の HSM が必要なら、CloudHSM を使った KMS のカスタムキーストアを構成する

## つまずきポイント

- 「KMS の鍵の中身は取り出せる」は間違い。鍵素材は KMS の外に出ず、非対称鍵でも取り出せるのは公開鍵だけ。
- 「KMS を使うなら、キーポリシーと IAM ポリシーの2枚が常に要る」は間違い。同じアカウントでは、キーポリシーが直接許可していれば IAM は不要で、委任していれば IAM だけで足りる。2枚が要るのは別アカウントのとき。
- 「S3 の既定の暗号化は KMS を使う」は間違い。既定の SSE-S3 は KMS を使わない。
- 「AWS マネージドキーなら料金はかからない」は間違い。月額はかからないが、API リクエストの分は請求される。
- 「FIPS のレベルが高いから CloudHSM を選ぶ」は間違い。KMS も CloudHSM もレベル3 で、差は占有性と鍵の扱い方にある。
- 「パラメータストアでも秘密情報は自動で入れ替わる」は間違い。標準では自動ローテーションがなく、定期更新は Secrets Manager の役目。
