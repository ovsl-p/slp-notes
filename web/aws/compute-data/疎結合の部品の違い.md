# 疎結合の部品の違い

## ひとことで

送る側と受ける側の間に置いて、速さの差や障害の影響を吸収する部品。使い方は、溜める、配る、振り分ける、順に進める、流れを受けるの5つに分かれる。

## なぜ効くか / どこで使うか

障害に強い構成を作るときの中心になる部品。送る側が受ける側の状態を気にしなくてよいので、どちらかが遅れても、もう一方は止まらない。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| 同期 | 送って、返事を待つ。相手が遅いと自分も待つ。 |
| 非同期 | 送って、すぐ次へ進む。相手は後で受け取る。 |
| キュー | 先に入れたメッセージを先に取り出す。順番に溜めて渡す。 |
| 冪等性 | 同じメッセージを2回受けても、結果を1回分にする。多くのキューは少なくとも1回届くので、受ける側で重複を扱う。 |

## 本体の解説

### 1. 役割で分ける

| 目的 | サービス | 特徴 |
|---|---|---|
| 溜めて、1つずつ処理する | SQS | キュー。受ける側が取りに来るまで保管し、速さの差を吸収する |
| 1つの出来事を複数に配る | SNS | 通知。登録された購読先へ push する |
| 出来事を条件で振り分ける | EventBridge | イベントバス。パターンに合うものだけ、対象へ届ける |
| 複数の手順を順に進める | Step Functions | 状態機械。途中の状態と再試行を管理する |
| 流れ続けるデータを受ける | Kinesis | ストリーム。順序を保ち、複数の読み手が後から読める |

### 2. SQS（キュー）

SQS は、受ける側が取りに来るまでメッセージを保管する。受ける側は、ポーリングで取り出して、処理が終わったら削除する。

標準キューは、順序を保証せず、少なくとも1回届く。スループットはほぼ無制限。FIFO キューは、順序を保ち、同じメッセージを重複して処理しないようにする。ただしスループットは標準より低い。名前の末尾は `.fifo`。

処理に失敗したメッセージは、可視性タイムアウトが過ぎると再び見えるようになる。何度も失敗するものは、デッドレターキュー（DLQ）に移して、原因を調べる。

### 3. SNS（通知）

SNS は、1回の Publish を、登録された複数の購読先へ配る。購読先は SQS、Lambda、HTTPS、メールなど。

SNS のトピックに複数の SQS キューを購読させると、1つの出来事を、独立した複数の処理へ同時に渡せる。この配り方をファンアウトと呼ぶ。購読先ごとに、フィルターポリシーで受け取る内容を絞れる。

標準トピックはメッセージを保管しない。配信に失敗したときの再試行の方針は、購読先の種類によって異なる。溜めて後で処理したいなら、SQS と組み合わせる。FIFO トピックだけは、1〜365日のアーカイブと、購読側での再生ができる。

### 4. EventBridge（イベントのルーティング）

EventBridge は、イベントバスに流れてくる出来事を、ルールのパターンで選んで、対象へ届ける。AWS のサービスの状態変化（例: EC2 の停止）や、SaaS からのイベントも扱える。

スケジュール（定時実行）も、同じルールで書ける。

SNS は登録された購読先へ配り、EventBridge はルールに合う出来事だけを選んで届ける、と覚えると分けやすい。

### 5. Step Functions（処理の流れ）

Step Functions は、複数の処理を状態として並べて、順序、分岐、並列、再試行、エラー処理を定義する。

- Standard: 最長1年実行できる。各ステップは正確に1回だけ実行される
- Express: 大量で短い処理向け。料金は実行回数と時間で決まる。

Lambda を直接つなぐと、途中の状態や再試行を自前で書くことになる。流れを見える形で管理したいなら、Step Functions が向く。

### 6. Kinesis（ストリーム）

Kinesis は、途切れずに流れるデータを受ける。

- Data Streams: 順序を保って保管する（保持は既定で24時間、最長365日）。複数の読み手が、それぞれの速さで読める。過去の分を読み直せる。
- Data Firehose: 受けたデータを、S3、Redshift、OpenSearch などへ、ほぼリアルタイムで運ぶ。自分で読み手を書く必要はないが、読み直しはできない。

SQS との違いは、複数の読み手が同じデータを読めるか、読み終えたデータをもう一度読み直せるかである。

### 7. 選び方の順番

1. 処理を溜めて、1つずつ確実に処理したい → SQS（順序と重複が要るなら FIFO）
2. 1つの出来事を、複数の処理へ同時に配りたい → SNS（と SQS で溜める）
3. 出来事を条件で振り分けたい、SaaS や定時実行 → EventBridge
4. 複数の手順を、再試行や分岐つきで順に進めたい → Step Functions
5. 流れ続けるデータを、複数の読み手で読みたい、読み直したい → Kinesis Data Streams。S3 などへ運ぶだけなら Data Firehose

#### Amazon MQ が要る場面

既存のブローカーを移行する場面では、Amazon MQ が候補になる。Apache ActiveMQ Classic と RabbitMQ のマネージドブローカーで、メッセージングのコードを書き換えずに移行できる。

ActiveMQ ブローカーは AMQP、MQTT、MQTT over WebSocket、OpenWire、STOMP、STOMP over WebSocket を使える。JMS はもともと ActiveMQ の主な用途で、OpenWire 経由でつながる。RabbitMQ ブローカーは AMQP 0-9-1 と AMQP 1.0 を使える。JMS 1.1、JMS 2.0、JMS 3.1 は RabbitMQ 4 以降で、RabbitMQ JMS クライアントを使うときに限って使える。サーバーセッション、XA トランザクション、キュー宛ての JMS セレクタ、NoLocal は使えない。JMS 2.0 以降で追加された API では、配送遅延（setDeliveryDelay）も使えない。

SQS、SNS、EventBridge は AWS 固有の API で使い、JMS、AMQP、MQTT、STOMP といった標準プロトコルは持たない。SQS には JMS 1.1 のクライアントライブラリ（Amazon SQS Java Messaging Library）があるが、使えるのはキューへの送受信の一部だけで、MQTT や STOMP は扱えない。

既存の JMS アプリや MQTT のデバイスがそのままつながる必要がある場面では、Amazon MQ が選択肢に入る。新規に AWS 内で完結するシステムなら、SQS や SNS のほうが管理の手間が少なくて済む。

ブローカーの構成はエンジンで分かれる。ActiveMQ は、1つの AZ のシングルインスタンスか、2つの AZ に置いたアクティブ/スタンバイの冗長ペアから選ぶ。アクティブ/スタンバイは共有ストレージに EFS を使う。EBS は AZ 内の複製だけなのでアクティブ/スタンバイには使えないが、シングルインスタンスなら選べる。RabbitMQ は、1つの AZ のシングルインスタンス（EBS）か、3つのノードを複数の AZ に置くクラスターから選ぶ。

## 具体例・コード

注文の受付を例にする。

1. 注文は、API から SQS に溜める。受付は止めずに済む
2. 注文確定の出来事は、SNS に Publish する
3. 通知、分析、監査の3つの SQS が、SNS からそれぞれ購読する
4. 通知の処理が失敗したら、DLQ に移して再試行や調査をする
5. 在庫確保、決済、発送の手順は、Step Functions で管理する。SNS の購読先にはしない

## つまずきポイント

- 「SQS の標準キューは順序が保証される」は間違い。標準キューは順序を保証しない。順序が要るなら FIFO を使う。
- 「SQS は重複しない」は間違い。標準キューは少なくとも1回届くので、受ける側を冪等にする。
- 「SNS は、受け取り手がいなくてもメッセージを保管する」は間違い。標準トピックは保管しない。溜めたいなら SQS と組み合わせる（FIFO トピックはアーカイブできる）。
- 「EventBridge と SNS は同じ用途だ」は間違い。SNS は全員に配る。EventBridge は条件に合うものを対象に届ける。
- 「Kinesis Data Firehose で、過去のデータを読み直せる」は間違い。読み直しは Data Streams の機能で、Firehose は読み直せない。
- 「SQS、SNS、EventBridge は JMS や MQTT の標準プロトコルでつながる」は間違い。3つは AWS 固有の API で使う。SQS の JMS 1.1 クライアントは送受信の一部だけを扱い、MQTT と STOMP は扱えない。
