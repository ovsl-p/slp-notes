# 疎結合の部品の違い

## ひとことで

送る側と受ける側の間に置いて、速さの差や障害の影響を吸収する部品。使い方は「1対1で溜める」「1対多に配る」「条件でルーティングする」「順に流す」「流れを連続で受ける」の5つで分かれる。

## なぜ効くか / どこで使うか

分野1で「障害時に壊れない構成」を選ばせる設問の中心になる。送る側が受ける側の状態を気にせずに済むと、一方が遅れても止まらなくなる。

## 前提となる知識

- 同期: 送って、返事を待つ。相手が遅いと自分も待つ。
- 非同期: 送って、すぐ次へ進む。相手は後で受け取る。
- 冪等性: 同じメッセージを2回受けても、結果が1回分になるように作ること。多くのキューは「少なくとも1回」届くので、受ける側で重複を扱う必要がある。

## 本体の解説

### 1. 役割で分ける

| 目的 | サービス | 一言で |
| --- | --- | --- |
| 溜めて、1つずつ処理する | SQS | キュー。送る側と受ける側の速さの差を吸収する |
| 1つの出来事を複数に配る | SNS | 通知。Publish すると、登録された先へ push する |
| 出来事を条件で振り分ける | EventBridge | イベントバス。パターンに合うものだけ、対象へ届ける |
| 複数の手順を順に進める | Step Functions | 状態機械。途中の状態と再試行を管理する |
| 流れ続けるデータを受ける | Kinesis | ストリーム。順序を保ち、複数の読み手が後から読める |

### 2. SQS（キュー）

SQS は、受ける側が取りに来るまでメッセージを保管する。受ける側は、ポーリングで取り出して、処理が終わったら削除する。

**標準キュー**は、順序を保証せず、少なくとも1回届く。スループットはほぼ無制限。
**FIFO キュー**は、順序を保ち、重複を防ぐ（1回の処理）。ただしスループットは標準より低い。名前の末尾は `.fifo`。

処理に失敗したメッセージは、可視性タイムアウトが過ぎると再び見えるようになる。何度も失敗するものは、**デッドレターキュー（DLQ）**に移して、原因を調べる。

### 3. SNS（通知）

SNS は、1回の Publish を、登録された複数の購読先へ配る。購読先は SQS、Lambda、HTTPS、メールなど。

SQS を複数購読させると、1つの出来事を、独立した複数の処理へ同時に渡せる。これを**ファンアウト**と呼ぶ。購読先ごとに、フィルターポリシーで受け取る内容を絞れる。

標準トピックは保管しない。届かなかった分の再試行は、購読先の種類によって決まる。溜めて後で処理したいなら、SQS と組み合わせる。FIFO トピックだけは、1〜365日のアーカイブと、購読側での再生ができる。

### 4. EventBridge（イベントのルーティング）

EventBridge は、イベントバスに流れてくる出来事を、ルールのパターンで選んで、対象へ届ける。AWS のサービスの状態変化（例: EC2 の停止）や、SaaS からのイベントも扱える。

スケジュール（定時実行）も、同じルールで書ける。

SNS は「全員に配る」、EventBridge は「条件に合うものを、対象に届ける」と覚えると、分けやすい。

### 5. Step Functions（処理の流れ）

Step Functions は、複数の処理を状態として並べて、順序・分岐・並列・再試行・エラー処理を定義する。

- **Standard**: 最長1年まで走れる。1回だけ実行されることが保証される。
- **Express**: 大量で短い処理向け。料金は実行回数と時間で決まる。

Lambda を直接つなぐと、途中の状態や再試行を自前で書くことになる。流れを見える形で管理したいなら、Step Functions が向く。

### 6. Kinesis（ストリーム）

Kinesis は、途切れずに流れるデータを受ける。

- **Data Streams**: 順序を保って保管する（保持は既定で24時間、最長365日）。複数の読み手が、それぞれの速さで読める。過去の分を読み直せる。
- **Data Firehose**: 受けたデータを、S3、Redshift、OpenSearch などへ、ほぼリアルタイムで運ぶ。自分で読み手を書く必要はないが、読み直しはできない。

SQS との違いは、読み手が複数いるか、読み直すかどうか。

### 7. 選び方の順番

1. 処理を溜めて、1つずつ確実に処理したい → SQS（順序と重複が要るなら FIFO）
2. 1つの出来事を、複数の処理へ同時に配りたい → SNS（+ SQS で溜める）
3. 出来事を条件で振り分けたい、SaaS や定時実行 → EventBridge
4. 複数の手順を、再試行や分岐つきで順に進めたい → Step Functions
5. 流れ続けるデータを、複数の読み手で読みたい、読み直したい → Kinesis Data Streams。S3 などへ運ぶだけなら Data Firehose

#### Amazon MQ が要る場面

既存のブローカーを移行する場面では Amazon MQ が候補になる。Amazon MQ は Apache ActiveMQ Classic と RabbitMQ のマネージドブローカーで、メッセージングのコードを書き換えずに移行できる。ActiveMQ ブローカーは AMQP、MQTT、MQTT over WebSocket、OpenWire、STOMP、STOMP over WebSocket を使える。RabbitMQ ブローカーは AMQP 0-9-1、AMQP 1.0、JMS 1.1、JMS 2.0、JMS 3.1 を使える。

SQS、SNS、EventBridge は AWS 固有の API で使い、JMS、AMQP、MQTT、STOMP といった標準プロトコルは持たない。既存の JMS アプリや MQTT のデバイスがそのままつながる必要がある場面では、Amazon MQ が選択肢に入る。新規に AWS 内で完結するシステムなら、SQS や SNS の方が管理の手間が少なくて済む。ブローカーの構成は、1つの AZ のシングルインスタンスか、2つの AZ に冗長化したアクティブ/スタンバイ（EFS を使用）から選ぶ。

## 具体例・コード

注文の受付の例。

1. 注文は、API から SQS に溜める。受付は止めずに済む
2. 注文確定の出来事は、SNS に Publish する
3. 通知、分析、監査の3つの SQS が、SNS からそれぞれ購読する
4. 通知の処理が失敗したら、DLQ に移して再試行や調査をする
5. 在庫確保、決済、発送の手順は、Step Functions で管理する。SNS の購読先にはしない

## つまずきポイント

- SQS の標準キューは順序が保証されると思う。保証されないので、順序が要るなら FIFO。
- SQS は重複しないと思う。標準キューは少なくとも1回届くので、受ける側を冪等にする。
- SNS は、受け取り手がいなくてもメッセージを保管すると思う。標準トピックは保管しない。溜めたいなら SQS と組み合わせる（FIFO トピックはアーカイブできる）。
- EventBridge と SNS を同じ用途だと思う。SNS は配る、EventBridge は条件で届ける。
- Kinesis Data Firehose で、過去のデータを読み直せると思う。読み直しは Data Streams の機能。
