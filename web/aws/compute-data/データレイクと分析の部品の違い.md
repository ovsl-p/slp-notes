# データレイクと分析の部品の違い

## ひとことで

データレイクは、生のデータを S3 にそのまま置く層である。その上に台帳、権限、問い合わせ、流し込み、可視化の部品を重ねて分析を組み立てる。

## なぜ効くか / どこで使うか

データを先に置き、読むサービスを後から選べる。同じ S3 のデータを、Athena で単発に問い合わせ、EMR でまとめて処理し、Redshift Spectrum では DWH から直接結合できる。置き場と読み手を分けると、サービスごとにデータを複製し直さなくて済む。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| S3 | AWS のオブジェクトストレージ。ファイルを置く場所。 |
| データウェアハウス（DWH） | 集計や分析に向けて整えたデータの保管庫。 |
| SQL | 表形式のデータに問い合わせるための言語。 |
| ETL | データを抽出し、変換して、別の場所へ格納する処理。 |
| スキーマ | テーブルの列名と型の定義。 |
| メタデータ | データの場所や形式などを説明するデータ。 |
| バッチ処理 | 溜まったデータをまとめて定期的に処理する方式。 |
| ストリーム処理 | 発生したデータを流れるまま順に処理する方式。 |
| Hadoop / Spark | 大量データを複数のサーバで分散処理する仕組みと、その処理エンジン。 |
| BI | 集計結果をグラフなどにして見せる用途。 |

## 本体の解説

![[assets/web/data-lake-parts.svg]]

S3 に置いたデータを、台帳と権限の層が「表」に変え、問い合わせる側はその表だけを見る。

### 1. 置く: S3 がデータレイクの土台

データレイクの置き場は S3 である。生のデータをそのまま置き、加工は必要になってから行う。形式を先に決めないため、取り込みを早く進められる。

### 2. 台帳: Glue Data Catalog

AWS Glue Data Catalog は、テーブルの定義とスキーマをまとめた台帳である。Athena、EMR、Redshift Spectrum が同じ台帳を参照する。どのサービスからも、同じテーブル名で同じデータを読める。

Glue はサーバーレスのデータ統合サービスである。70以上のデータソースにつながり、ETL ジョブとクローラを持つ。クローラが S3 を読んで、台帳にテーブル定義を登録する。

### 3. 権限: Lake Formation

AWS Lake Formation は、データレイクの権限を一元管理する。列、行、セル単位の細かい制御ができる。Glue Data Catalog のメタデータも制御の対象になる。

権限は Athena、Redshift Spectrum、EMR、Glue に効く。ただし EMR と Glue のジョブは、Lake Formation との連携を有効にしたときに限る。どのサービスでも、対象の S3 の場所を Lake Formation に登録しておく必要がある。読み手ごとに見せる列を変える運用は、ここで設計する。

### 4. 問い合わせる: Athena、Redshift、EMR

Amazon Athena は、S3 に直接 SQL を投げる対話型のクエリサービスである。SQL クエリは、スキャンしたデータ量に対して課金される。Athena では Apache Spark も動き、Spark の計算は DPU 時間で課金される。計算容量を予約する Provisioned Capacity は、DPU 時間で課金される。

Amazon Redshift は、ペタバイト級のデータウェアハウスである。プロビジョンドと Serverless があり、Serverless はクエリを処理していない時間の計算料金がかからない。ストレージは保存量に応じて別に課金される。Redshift Spectrum は、S3 上のデータをロードせずに DWH から問い合わせる。

Amazon EMR は、Hadoop と Spark を動かすマネージドのクラスタである。S3 や DynamoDB とデータをやり取りする。大量データの加工に向く。

### 5. 流す: Kinesis、MSK、AppFlow

Amazon Kinesis Data Streams は、大量のデータレコードをリアルタイムに集めて処理するストリームである。読み取る側のアプリケーションをコンシューマーと呼び、ダッシュボードやアラート、他の AWS サービスへ渡す。

Amazon Data Firehose は、ストリームのデータを S3、Redshift、OpenSearch、Iceberg などへ配送する。配送前の変換もできる。Data Streams がストリームそのもので、Firehose は届ける役割である。

Amazon MSK は、Apache Kafka のマネージドサービスである。Kafka を使う既存の仕組みがある場合は、取り込みに MSK を選ぶ。Amazon AppFlow は、SaaS から S3 などへデータを取り込む。

### 6. 見せる: AWS Quick Sight

AWS Quick Sight（旧 Amazon QuickSight）は、AWS Quick の中の BI 機能である。集計済みのデータを受けて、グラフや表にする。データレイクの置き場の役割は持たないが、表示を速くするために SPICE というインメモリのエンジンへ取り込んで保持できる。

名前は2段階で変わった。2025年10月に Amazon QuickSight が Amazon Quick Suite になり、BI 機能が Quick Sight に分かれた。2026年11月に、サービス名が AWS Quick、BI 機能が AWS Quick Sight になった。既存のダッシュボードやデータセットはそのまま使える。

### 7. Iceberg は S3 の上に表として扱える形式

Apache Iceberg は、オープンなテーブル形式である。S3 の上に置けて、表として扱える。Athena では読み書きができ、タイムトラベルで過去の時点のデータを参照できる。

Iceberg は計算エンジンではなく、データの持ち方の規約である。同じテーブルを Athena や EMR から読める余地が生まれる。

### 8. バッチとストリームの違い

バッチは、データを溜めてから一定の周期でまとめて処理する方式である。注文ログを日次で集計する場合がこれに当たる。処理結果は、次の周期まで古いままになる。

ストリームは、データが発生するたびに流して処理する方式である。Kinesis や MSK でデータを受け、Firehose で配送するか、後段で即座に処理する。結果は数秒から数分の遅れで見える構成を組める。

両者は同じデータに対して併用できる。同じ注文ログを、バッチで日次集計し、ストリームで即時に見る構成が典型である。

## 具体例・コード

注文ログを S3 に溜めて、日次で集計するバッチ経路。

1. アプリが注文ログを S3 の raw 領域に書き出す。raw 領域は、加工前のデータを置くフォルダに付ける慣習的な名前で、AWS の機能名ではない。
2. Glue クローラが S3 を読み、Glue Data Catalog にテーブル定義を登録する。
3. raw 領域を Lake Formation に登録し、既定で付いている IAMAllowedPrincipals の権限を外す。既定のままだと、IAM で許可されたロールは列の制限を受けずに全列を読める。
4. Lake Formation で、分析者のロールに見せる列を限定する。
5. EventBridge Scheduler から日次で Athena の SQL を実行し、集計結果を別のテーブルに書き込む。Athena に定期実行の機能はない。
6. Quick Sight で集計結果をグラフにする。

```sql
-- orders_daily は事前に作っておく
INSERT INTO orders_daily
SELECT order_date, SUM(amount) AS total_amount
FROM orders_raw
WHERE order_date = '<対象日>'
GROUP BY order_date;
```

同じ注文ログを、ストリームで即時に見る経路。

1. アプリが注文イベントを Kinesis Data Streams へ送る。
2. Data Firehose がストリームを受け、配送先の S3 へ書き出す。
3. 即時に見たい指標は、Firehose から OpenSearch へも配送する。
4. S3 に書いた分の閲覧範囲は Lake Formation の権限で、OpenSearch へ送った分は OpenSearch のアクセスポリシーと fine-grained access control で決める。

## つまずきポイント

- 「S3 に置けばデータレイクの分析は終わる」は間違い。S3 は置き場にすぎず、台帳、権限、問い合わせの層が別に要る。
- 「Glue と Glue Data Catalog は同じもの」は間違い。Glue は ETL を含むサービスで、Data Catalog はその中の台帳にあたる。
- 「Athena は起動している時間で課金される」は間違い。SQL クエリはスキャンしたデータ量に対して課金され、クエリを投げなければかからない。
- 「Lake Formation で権限を付ければ列は絞れる」は間違い。既定では新しいテーブルに IAMAllowedPrincipals の権限が付き、IAM で許可されたロールは全列を読める。先にその権限を外す。
- 「Redshift Spectrum は S3 のデータをロードしてから問い合わせる」は間違い。Spectrum はロードせずに S3 へ問い合わせる。
- 「Lake Formation は列と行だけ制御できる」は間違い。セル単位まで制御でき、Glue Data Catalog のメタデータも対象になる。
- 「Kinesis Data Streams と Data Firehose は同じ役割」は間違い。Data Streams はストリームそのもので、Firehose は配送先へ届ける役割である。
