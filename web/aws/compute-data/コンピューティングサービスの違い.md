# コンピューティングサービスの違い

## ひとことで

どこまで自分で管理するかと、いつ動くかの2軸でサービスを選ぶ。常時なら EC2、イベントなら Lambda、コンテナなら ECS か EKS。

## なぜ効くか / どこで使うか

ワークロードの性質（常時か、突発的か、長いか短いか、コンテナか）を読んで、動かす場所を選ぶ場面で効く。費用と運用の手間の両方が判断材料になる。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| 仮想マシン | 1台の物理機械の中に、OS ごと独立した機械を複数動かす仕組み。EC2 はこれを借りる。 |
| コンテナ | アプリとその依存をひとまとめにした箱を、OS の中で隔離して動かす仕組み。 |
| イベント駆動 | 出来事（リクエスト、ファイル追加、キューのメッセージ）が来たときだけ処理する仕組み。 |
| スロットリング | 同時実行数の上限を超えた呼び出しを制限する仕組み。 |

## 本体の解説

### 1. 管理の範囲で分ける

| 管理の範囲 | サービス | 特徴 |
|---|---|---|
| OS まで自分で管理 | EC2 | 仮想サーバーを借りる。最も自由 |
| コンテナだけ管理 | ECS、EKS | コンテナを動かす。Fargate ならサーバーの管理は不要 |
| 関数だけ書く | Lambda | 呼ばれたときだけ、コードを実行する |
| アプリだけ渡す | Elastic Beanstalk | デプロイと管理を任せる。実体は EC2 などで動く |

### 2. EC2（仮想サーバー）

EC2 は、インスタンスタイプ（CPU、メモリ、ネットワークの組み合わせ）を選んで起動する。

購入オプションで費用が変わる。

- オンデマンド: 使った分だけ。計画が立たないとき。
- Savings Plans、リザーブドインスタンス: 1年や3年の約束で割引。常に動く分に向く。
- スポットインスタンス: 空いている容量を安く使う。途中で止められることがあるので、途中から再開できる処理に向く。
- 専有ホスト: 物理ホストを占有する。ライセンスの要件などで使う。

プレイスメントグループは、インスタンスの配置方針を決める。種類は3つある。

- クラスター: 近くに置いて、遅延を小さくする
- スプレッド: 別々のハードウェアに置いて、障害の影響を分ける
- パーティション: ラックごとに分けて置く。大規模な分散処理に向く

### 3. Auto Scaling（台数を自動で増減）

Auto Scaling は、負荷に合わせて EC2 の台数を増減する。複数の AZ にまたがって台数を配り、ヘルスチェックで異常なインスタンスを置き換える。

- ターゲットトラッキング: CPU 使用率などの目標値を保つ。最もよく使われる。
- スケジュール: 決まった時間に増やす。
- 予測: 過去のパターンから先に増やす。

ELB と組み合わせると、台数の増減が利用者から見えなくなる。

### 4. Lambda（イベントで実行）

Lambda は、関数を呼び出されたときだけ動かす。サーバーの管理はいらず、実行回数と時間で料金がかかる。

制限を押さえておく。

- 1回の実行は、オンデマンドの Event Functions で最長30分。Web Functions は15分、Lambda Managed Instances の非同期呼び出しとイベントソースマッピングは90分になる。長い処理には向かない。
- メモリは128 MB から10 GB まで。CPU はメモリに比例して割り当てられる。
- 同時実行数に上限があり、超えるとスロットリングされる。同期呼び出しには 429 TooManyRequestsException が返り、非同期呼び出しは Lambda が再試行する。

SQS、S3、EventBridge、API Gateway などから直接呼ばれる。

### 5. ECS と EKS（コンテナの管理）

ECS は AWS 独自のコンテナ管理。EKS は Kubernetes のマネージド版。

違いは、Kubernetes の知識や移植性が必要かどうかである。Kubernetes のツールや仕組みを使いたいなら EKS を選ぶ。AWS の中で完結させるなら、ECS のほうが運用は軽くなりやすい。

起動の場所も選べる。

- EC2 上で動かす: サーバーの台数を自分で管理する
- Fargate で動かす: サーバーの管理が不要になる。CPU とメモリは、タスク（EKS では Pod）単位で指定する

### 6. Elastic Beanstalk（アプリを渡す）

Elastic Beanstalk は、アプリのコードを渡すと、EC2、ELB、Auto Scaling を組み立てて動かす。インフラの細かい設定は意識せずに済むが、その分、自由に変更するのは難しい。

素早く Web アプリを動かしたいときや、インフラの知識が少ないときに向く。

### 7. 選び方の順番

1. イベントで動き、1回の処理が30分以内（オンデマンド） → Lambda
2. コンテナで動かす → ECS（AWS の中で完結）か EKS（Kubernetes が要る）。サーバー管理を避けたいなら Fargate
3. OS の設定やソフトウェアを自由に入れたい → EC2（と Auto Scaling）
4. 負荷に合わせて増減する → Auto Scaling を組み合わせる
5. 費用を下げたい → 常に動く分は Savings Plans、途中で止まってもよい処理はスポット

## 具体例・コード

画像のアップロード処理を例にする。

1. 画像のアップロードは S3 に置く。イベントが出る
2. サムネイルの作成は Lambda で行う。数秒で終わるので、30分の制限に収まる
3. 動画の変換は時間がかかるので、ECS か AWS Batch のコンテナで行う。途中で止まっても再開できるなら、スポットで費用を下げられる
4. Web の API は ECS（Fargate）で動かし、負荷に合わせてタスク数を増やす

## つまずきポイント

- 「Lambda で長い処理を動かせる」は間違い。オンデマンドの Event Functions でも1回の実行は最長30分（Web Functions は15分）で、長い処理には向かない。
- 「スポットインスタンスは安定した処理に向く」は間違い。途中で止められることがあるので、再開できる処理に向く。
- 「Auto Scaling は1つの AZ だけで台数を増やす」は間違い。複数の AZ に配るのが基本。
- 「Fargate と EKS は同じもの」は間違い。Fargate は起動の場所、EKS は管理する仕組みで、組み合わせて使える。
- 「Elastic Beanstalk は基盤を細かく作り込める」は間違い。細かい調整は限られる。本番でも使われる。
