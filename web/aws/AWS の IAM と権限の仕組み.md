# AWS の IAM と権限の仕組み

## ひとことで

誰が・何を・どのリソースにできるかをポリシーで書き、明示的な拒否が最優先で、書き忘れは全部拒否になる。

## なぜ効くか / どこで使うか

403 が出たとき、S3 が読めないとき、別アカウントから届かないとき、原因はほぼこの評価の順番にある。IAM は SAP-C03 の全分野の前提で、SCP や RCP の話も、まずここが分かっていないと読めない。

実務でも、権限を足すより「なぜ足りないのか」を説明できるほうが強い。評価の順番を知っていれば、足す場所を間違えない。

## 前提となる知識

| 知っておくこと | なぜ必要か |
| --- | --- |
| 認証と認可 | 「誰か」を決めるのが認証、「何をしてよいか」が認可。IAM は後者 |
| プリンシパル | 操作する側（ユーザー、ロール、AWS のサービス） |
| JSON | ポリシーは JSON。Effect / Action / Resource の3つが骨格 |
| 一時認証情報 | 期限つきの鍵。ロールを使うとこれが手に入る |

## 本体の解説

判定の3段と、クロスアカウントで両側が要る理由。

![[assets/web/aws-iam-evaluation.svg]]

### 1. 3つの登場人物

操作する側をプリンシパル、操作される側をリソース、その間を決めるのがポリシーになる。

ポリシーは2種類ある。プリンシパルに貼るものをアイデンティティベース、リソースに貼るものをリソースベースと呼ぶ。S3 のバケットポリシーや KMS のキーポリシーが後者になる。

リソースベースのポリシーだけが `Principal` を書ける。誰に許すかをリソース側から指定できるのはこちらだけになる。

### 2. 評価の順番

判定は次の順になる。

1. どこかに明示的な拒否（`Deny`）があれば、その時点で拒否
2. 上限（SCP・RCP・権限の境界・セッションポリシー）のすべての中で許可されていて、かつアイデンティティかリソースのポリシーで許可されていれば許可
3. どれかで許可が無ければ拒否（暗黙の拒否）

許可は足し算で、上限は掛け算になる。上限の中に Allow が無ければ、アイデンティティ側で許可していても止まる。SCP や境界で止まるのは、ほとんどがこの暗黙の拒否で、明示的な `Deny` ではない。

だから「許可を足したのに効かない」ときは、明示的な拒否を先に探し、次に上限のどこで許可されていないかを見る。組織の SCP、バケットポリシーの拒否、KMS のキーポリシー、境界のどれかが効いている。

### 3. ロールと AssumeRole

ロールは「権限の束」で、人にもサービスにも、別アカウントにも貸せる。

引き受けるときは STS の `AssumeRole` を呼ぶ。返ってくるのは期限つきの一時認証情報で、IAM ユーザーのアクセスキーのような長期の鍵ではない。

ロールには信頼ポリシーがある。「誰がこのロールを引き受けられるか」を書く場所で、権限を書くポリシーとは別物になる。ここを間違えると、権限は足りているのに AssumeRole が拒否される。

人の代わりに動く処理（CI、Lambda、EC2）は、基本すべてロールにする。鍵を配らないで済むのが最大の利点になる。

### 4. 上限をかける4つ

許可を絞る道具は、貼る場所が違う。

| 道具 | 何を縛るか | 誰が設定するか |
| --- | --- | --- |
| SCP | アカウント内のプリンシパルの操作 | 組織の管理者 |
| RCP | アカウント内のリソースへの操作 | 組織の管理者 |
| 権限の境界 | 1つのユーザーやロールの最大権限 | アカウントの管理者 |
| セッションポリシー | 引き受けたセッションの最大権限 | 引き受ける側 |

どれも「許可はしない、上限を下げるだけ」で、共通している。境界がどこまで効くかは、リソースベースのポリシーが誰に許可したかで変わる。同じアカウント内で IAM ユーザーやロールセッションの ARN に直接許可した場合は境界で止まらない。IAM ロールの ARN に許可した場合は、境界の暗黙の拒否で止まる。クロスアカウントのアクセスは呼び出し元の評価になるので、境界はそちら側にかかる。

SCP が組織の外からのリソースベースの許可を止められないのは、SCP が効くのがそのアカウントのプリンシパルだけだから。リソース側から上限をかけるのは RCP（resource control policy）で、RCP は自分のアカウントのリソースが外から触られる範囲を縛る。

### 5. クロスアカウントの2方向ルール

アカウントをまたぐときは、両側で許可が要る。

呼び出し元のアイデンティティに「このリソースを触ってよい」と書き、リソース側にも「このプリンシパルに許す」と書く。片方だけでは通らない。

ロールを引き受ける形なら、A 側で `sts:AssumeRole` を許可し、B 側の信頼ポリシーで A を信頼する。この2枚が揃って初めて鍵が返る。

SCP は、その SCP が付いたアカウントのプリンシパル（IAM ユーザーとロール）にだけ効く。B のバケットポリシーで A を許可している形では、効くのは A の SCP だけになる。B 側の SCP は、呼び出し元が B のプリンシパルではないので関与しない。B の組織で外からのアクセスを止めたいなら、RCP か `aws:PrincipalOrgID` の条件を使う。

B のロールを `AssumeRole` する形なら話が変わる。引き受けたセッションは B のプリンシパルになるので、そこで B の SCP も効く。

### 6. 条件キー

ポリシーには条件を書ける。これが実務で一番効く部分になる。

`aws:SourceIp` で接続元を絞る、`aws:PrincipalOrgID` で組織内だけに許す、`aws:MultiFactorAuthPresent` で MFA を要求する、`aws:RequestedRegion` で使えるリージョンを絞る、といった形で使う。

`aws:PrincipalOrgID` は、組織の外のアカウントからリソースベースのポリシー経由で来るアクセスを止める数少ない手段になる。SCP が効かない場面を、条件で埋める形になる。

### 7. 人が入る経路

人が複数アカウントに入るときは、IAM ユーザーを作らずに IAM Identity Center を使う。外部の IdP と連携して、権限セットをアカウントに割り当てる。

キーを配る運用をやめられるので、退職や異動のときに IdP 側を止めれば全部止まる。

## 具体例・コード

別アカウント B の S3 バケットを、アカウント A の Lambda から読む場合。

1. B のバケットポリシーに、A の Lambda 用ロールを `Principal` として `s3:GetObject` を許可する
2. A の Lambda のロールに、そのバケットへの `s3:GetObject` を許可する
3. バケットが KMS で暗号化されているなら、キーポリシーで A のロールに `kms:Decrypt` を許可し、A のロールの IAM ポリシーにも `kms:Decrypt` を足す。キーはカスタマーマネージドキーを使う（`aws/s3` などの AWS マネージドキーはキーポリシーを変えられないので、クロスアカウントでは使えない）
4. A の SCP で S3 が禁止されていないことを確認する。B 側で外からのアクセスを絞りたいなら、RCP も見る

どこか1つ欠けると 403 になる。403 が出たら、この4つのどこが欠けているかを順に潰す。3はキーポリシーと IAM ポリシーの2枚が要るので、片方だけ直して終わりにしない。

## つまずきポイント

- リソースベースのポリシーを書けば、呼び出し元の許可は要らないと思う。別アカウントでは両方要る。
- KMS を忘れる。S3 の許可が揃っていても、キーポリシーか自分の IAM ポリシーのどちらかが欠けていると読めない。
- 境界を、リソースベースの許可に対する万能のブレーキだと思う。止まるのは同じアカウント内でロールの ARN に許可した場合で、IAM ユーザーやロールセッションの ARN への許可は通る。
- SCP で何かを許可できると思う。SCP は上限を下げるだけで、許可はしない。
- アクセスキーを発行して配る。ロールで足りる場面がほとんどで、鍵は漏れる前提で扱うものになる。
- 拒否が効いているのに、許可を足して直そうとする。まず `Deny` を探す。
