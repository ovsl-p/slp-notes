# 災害対策の4つの型と切り替えの道具

## ひとことで

災害対策（DR）の型は、RPO・RTO・コストの3つで選ぶ。型ごとに、切り替えと複製の道具が決まる。

## なぜ効くか / どこで使うか

型を先に決めると、道具の選択が自然に絞られる。逆に道具から入ると、要件に合わない構成になりやすい。

使う場面は、リージョン障害やデータ破損に備える設計レビューである。オンプレや他のクラウドのサーバーを守る場面でも使う。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| RPO | 許容できるデータ損失の長さ。 |
| RTO | 復旧にかけてよい時間。 |
| アクティブ/パッシブ | 平常時は片方だけがトラフィックを受ける構成。 |
| アクティブ/アクティブ | 複数のリージョンが同時にトラフィックを受ける構成。 |
| コントロールプレーン | リソースを作る、変更するといった管理操作の層。 |
| データプレーン | 稼働中のリソースが実際に処理を行う層。 |
| IaC | インフラをコードで定義して展開する方式。CloudFormation や CDK が該当する。 |

DB やストレージの特性は [[データベースサービスの違い]] と [[ストレージサービスの違い]] にある。DNS の挙動は [[DNS と名前解決]] を参照する。

## 本体の解説

### 1. RPO と RTO の2軸

RPO が短いほど、データを常に複製しておく必要がある。RTO が短いほど、復旧先を常に動かしておく必要がある。どちらもコストに跳ね返る。この2つとコストの釣り合いで、型を選ぶ。

### 2. 4つの型

4つの型を、コストが低く復旧が遅い順に並べる。

| 型 | 平常時の状態 | 復旧時の動き |
|---|---|---|
| バックアップと復元 | バックアップを取るだけ | インフラを作り直し、データを戻す |
| パイロットライト | データを複製し、中核のインフラも用意する。アプリサーバーは止めておく | アプリサーバーを起動する |
| ウォームスタンバイ | 縮小版の環境を常時動かす | 環境を拡大する |
| マルチサイト アクティブ/アクティブ | 複数のリージョンで同時に処理する | 障害側にトラフィックを送らない |

バックアップと復元は、データの損失や破損への対策になる。リージョン災害にも使えるが、復旧先へインフラとコードを再展開する必要がある。IaC で展開していないと、復旧が長引く。

パイロットライトでは、複製に要る資源を常時オンにする。DB やオブジェクトストレージがそれである。アプリサーバーはコードと設定を入れて止めておく。起動するのは、テストかフェイルオーバーのときだけである。

マルチサイトは書き込みの扱いが3通りある。

- write global: 書き込みを1リージョンに集め、障害時に別のリージョンを昇格させる。
- write local: 最寄りのリージョンに書く。DynamoDB グローバルテーブルは、最終書き込み優先で競合を解決する。
- write partitioned: ユーザー ID などで書き込み先を分ける。

### 3. 切り替えの道具

パイロットライトとウォームスタンバイはアクティブ/パッシブ型で、Route 53 か Global Accelerator でトラフィックを切り替える。

Global Accelerator にはトラフィックダイヤルがある。エンドポイントグループ（リージョン）ごとに受ける割合を決められる。グループ内のエンドポイントへの配分は、重み（weights）で決める。

Amazon Application Recovery Controller（ARC）は、障害の範囲で使い分ける。

| 障害の範囲 | 使う機能 |
|---|---|
| 単一 AZ | ゾーナルシフト（手動で一時的にトラフィックを逃がす）、ゾーナルオートシフト |
| リージョン | ルーティングコントロール、リージョンスイッチ、レディネスチェック |

レディネスチェックは新規の受付を終了した。後継はリージョンスイッチの計画評価（plan evaluation）である。

フェイルオーバーは、データプレーンの操作だけで組むと可用性を高く保てる。コントロールプレーンは、可用性の設計目標がデータプレーンより低いためである。

### 4. 複製の道具

AWS Elastic Disaster Recovery（DRS）は、オンプレや他のクラウドのサーバーを、選んだリージョンのステージングエリアへ複製する。ステージングは安いストレージと最小限の計算で回す。

DRS では、時点復旧ができる。非破壊のテストやフェイルバックの訓練も繰り返せる。起動時には、AWS 上でネイティブに動くよう自動で変換される。

Aurora グローバルデータベースは、セカンダリを10リージョンまで持てる（2025年5月に5から増えた）。セカンダリの昇格は1分未満で済み、セカンダリ側から書き込みを転送する機能もある。

コンテナは、複数クラスタの構成で可用性と DR を組む。EKS でも ECS でも同じ考え方である。

### 5. 評価の道具

AWS Resilience Hub は、RTO と RPO の目標を定義し、現状を評価して、改善案を出す。Fault Injection Service（FIS）の実験も、Resilience Hub から作れる。

## 具体例・コード

社内の予約システムを想定する。要件は RTO 4時間、RPO 15分である。

1. 型を選ぶ。RPO 15分は、15分以下の間隔で走るバックアップ（PITR を含む）か、継続的な複製で満たす。RTO 4時間はアプリサーバーの起動時間を許容できるため、パイロットライトを選ぶ。
2. データを複製する。DB は Aurora グローバルデータベースにして、別リージョンにセカンダリを置く。オブジェクトストレージも複製する。
3. アプリサーバーを用意する。コードと設定を入れた状態で、止めておく。IaC で定義し、復旧先でも同じ形で展開できるようにする。
4. 切り替えを組む。Route 53 のヘルスチェックによる自動フェイルオーバーか、ARC のルーティングコントロールで、トラフィックを復旧先へ向ける。トラフィックダイヤルの手動調整やレコードの書き換えはコントロールプレーンの操作なので、これに頼らずデータプレーン側で切り替わる形にする。
5. 目標を評価する。Resilience Hub に RTO 4時間と RPO 15分を登録し、現状の構成を評価する。出た改善案を設計へ反映する。
6. 訓練する。FIS の実験で障害を起こし、アプリサーバーの起動からトラフィック切り替えまでを通しで試す。かかった時間を RTO と比べる。

## つまずきポイント

- 「バックアップと復元はリージョン災害に使えない」は間違い。使えるが、インフラとコードを復旧先へ再展開する必要がある。IaC がないと復旧が長引く。
- 「パイロットライトは全部止めておく型」は間違い。DB やオブジェクトストレージなど、複製に要る資源は常時オンである。止めるのはアプリサーバーである。
- 「ウォームスタンバイとパイロットライトは同じ」は間違い。ウォームスタンバイは縮小版の環境を常時動かし、フェイルオーバーで拡大する。
- 「マルチサイトは書き込みを必ず全リージョンで受ける」は間違い。write global は書き込みを1リージョンに集める。write partitioned は ID で書き込み先を分ける。
- 「フェイルオーバーはコントロールプレーンの操作で組めば十分」は間違い。コントロールプレーンは可用性の目標が低いため、データプレーンの操作だけで組む。
- 「DRS は AWS 上のサーバー専用」は間違い。オンプレや他のクラウドのサーバーを、選んだリージョンへ複製できる。
