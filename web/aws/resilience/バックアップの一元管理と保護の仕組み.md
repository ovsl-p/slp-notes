# バックアップの一元管理と保護の仕組み

## ひとことで

AWS Backup でバックアップを一か所に集め、ロックで削除と改変を防ぎ、復元テストと FIS で戻せることと耐えられることを確かめる。

## なぜ効くか / どこで使うか

バックアップは取るだけでは足りない。消される、書き換えられる、戻せない、の3つが起きると意味を失う。

AWS Backup が管理を一か所にまとめ、残りの3つがそれぞれの失敗を防ぐ。

使う場面は3つある。コンプライアンス要件で保管データの改ざん防止を求められるとき、複数アカウントのバックアップを統制したいとき、ランサムウェアや誤操作に備えたいときである。

DR の型そのものは [[災害対策の4つの型と切り替えの道具]] に書いた。本ノートはバックアップの運用と防御に絞る。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| AWS Backup | 複数サービスのバックアップを集中管理するサービス。 |
| バックアッププラン | スケジュールと保持期間を定義するポリシー。 |
| ボールト | バックアップの保管先。 |
| Organizations | 複数アカウントを束ねる管理構造。 |
| WORM | write once read many。書いたら消せず、上書きもできない方式。 |
| リーガルホールド | 保持期間とは別に、訴訟などのため削除を止める設定。 |
| カオスエンジニアリング | 障害をあえて起こし、弱点を先に見つける考え方。 |

S3 や EBS など保管先ごとの違いは [[ストレージサービスの違い]] にある。

## 本体の解説

### 1. 集中管理: AWS Backup

AWS Backup は、複数サービスのバックアップを一か所で管理する。バックアッププランでスケジュールと保持を定義し、コンソール、API、CLI のいずれからでも運用できる。

AWS Backup の管理外で取ったバックアップは、管理の対象にならない。一元管理したいサービスは、最初から AWS Backup で取る。

コピーの方向は2つある。

- クロスリージョンコピー: バックアップを別リージョンへ、手動またはスケジュールで複製する。
- クロスアカウントコピー: Organizations の管理構造の中で、複数アカウントへ複製する。

クロスアカウントでは、1つのリポジトリ用アカウントに集める fan-in も、各アカウントへ配る fan-out もできる。アカウントをまたいで管理できるので、バックアッププランを手作業で複製する必要がない。

統制の評価には AWS Backup Audit Manager を使う。組み込みのコントロールでバックアップの統制を評価し、レポートする。監査系サービスとの切り分けは [[検知と監査の違い]]、組織単位の統制は [[組織の統制サービスの違い]] を参照する。

### 2. 守る: 3つのロック

3つのロックは、守る対象が異なる。

| 仕組み | 守る対象 | 要点 |
|---|---|---|
| AWS Backup Vault Lock | ボールト | 保管先の変更と削除を止める |
| S3 Object Lock | S3 オブジェクト | WORM。保持期間とリーガルホールドで管理する |
| EBS スナップショットロック | EBS スナップショット | IAM 権限に関係なく削除できない |

Vault Lock にはコンプライアンスモードがある。ロックが有効になり猶予期間が過ぎると、顧客もアカウントの所有者も AWS も構成を変えられない。ロックに追加料金はないが、保管料は通常どおりかかる。保持期間が終わるまで削除できないので、保持設定を誤ると、その間の保管料を払い続けることになる。

S3 Object Lock は、一定期間または無期限に、削除と上書きを防ぐ。保持期間とリーガルホールドは、同じバージョンに両方付けられる。

EBS スナップショットロックは、ロック中も通常のスナップショットとして使えるほか、WORM 形式の保管にも使える。

### 3. 試す: 復元テストと FIS

復元テストは、リストアが実際に動くかを定期的に確かめる機能である。復元テストにも料金がかかる。

AWS Fault Injection Service（FIS）は、カオスエンジニアリングの考え方で、実際のリソースに障害を起こす実験を行う。FIS はテンプレートで障害を定義し、停止条件とロールバックの仕組みを持つため、本番でも安全に回せる。実際のリソースに作用するので、まず検証環境で試す。

### 4. 自己修復の部品

障害を検知して自動で直す部品は、次のとおりである。

- Auto Scaling のヘルスチェックによる入れ替え
- Route 53 のヘルスチェックによる切り離し
- AWS Config の自動修復
- EventBridge と Lambda による異常の検知と修復

FIS の実験は、障害時に自己修復が働くかを確かめる場にもなる。

## 具体例・コード

EC2、RDS、S3 を持つシステムを想定し、6ステップで組む。

1. AWS Backup でバックアッププランを作る。EC2、RDS、S3 を対象にし、スケジュールと保持を定義する。
2. クロスアカウントコピーを設定し、リポジトリ用アカウントへ fan-in で集める。必要ならクロスリージョンコピーも加える。
3. リポジトリ用アカウントのボールトに Vault Lock をかける。コンプライアンスモードを使う前に、保持期間を確認する。
4. S3 バケットには Object Lock、EBS スナップショットにはスナップショットロックを、必要に応じて使う。
5. 四半期に1回、復元テストを回し、リストアが動くことを確かめる。
6. 同じ四半期に、FIS の実験を検証環境で回し、問題がなければ本番へ広げる。結果は Audit Manager のレポートと合わせて見直す。

## つまずきポイント

- 「AWS Backup を使えば、すべてのバックアップが自動で集まる」は間違い。AWS Backup の管理外で取ったバックアップは対象外である。
- 「Vault Lock は、あとで設定を直せばよい」は間違い。コンプライアンスモードで猶予期間が過ぎると、AWS を含め誰も構成を変えられない。
- 「ロックしても、保持期間の途中で消せる」は間違い。ロック中は保持期間が終わるまで削除できず、誤設定は費用として残る。
- 「IAM の管理者権限があれば、ロック済みスナップショットも消せる」は間違い。スナップショットロックは IAM 権限に関係なく削除を止める。
- 「S3 Object Lock は、保持期間かリーガルホールドのどちらか一方しか使えない」は間違い。両方を同じバージョンに付けられる。
- 「FIS は本番で試すものだから、検証環境は不要」は間違い。実際のリソースに作用するので、まず検証環境で試す。
