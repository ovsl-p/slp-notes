# クラウド移行の戦略と道具

## ひとことで

クラウド移行は、アプリごとに7つの戦略（7R）から1つを選び、依存関係でまとめた波に分けて進める作業である。移す、残す、やめる、作り直すを判断するのが本質になる。

## なぜ効くか / どこで使うか

アプリごとに事業価値も技術的な状態も違う。全部を同じ方法で移すと、無駄な作業と移行リスクが増える。戦略を分けて選ぶと、移行の手間と効果の釣り合いを取れる。

数十本規模の社内システムを移す計画を立てる場面で使う。棚卸しをして戦略を割り当て、移行の順番を決める。SAP-C03 の設計問題では、要件から適切な戦略を選ぶ判断が問われる。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| オンプレミス | 自社のデータセンターなどで動かす従来の環境。 |
| SaaS | インターネット経由で提供される完成済みのアプリケーション。 |
| 専用ハードウェア | 特定の機器に依存し、クラウドへ移しにくい構成要素。 |
| SDDC | VMware の仮想化基盤一式で構成されたデータセンター。 |
| スキーマ | テーブル構造などのデータベースの定義。 |
| CDC | 変更データキャプチャ。移行中や移行後の変更を継続的に取り込む仕組み。 |
| 依存関係 | アプリ同士が呼び合い、影響し合う関係。 |
| 技術的負債 | 古い設計や保守しにくい実装が積み重なった状態。 |

## 本体の解説

### 1. 7R の一覧

| 戦略 | 内容 | 例 |
|---|---|---|
| Retire | そのアプリをやめる。 | 使われていない業務システムの停止 |
| Retain | 今は移さず、オンプレに残す。 | 最近更新したばかり、移す事業価値がない、SaaS 版の提供待ち、専用ハードウェアに依存している |
| Rehost（lift and shift） | アプリを変えずに AWS へ移す。 | VM 単位での移行 |
| Relocate | オンプレのプラットフォームを、そのクラウド版へまとめて移す。 | VMware の SDDC から VMware Cloud on AWS へサーバー群を移す |
| Repurchase（drop and shop） | アプリを別の製品や SaaS に置き換える。 | 自社製のメール基盤から SaaS へ切り替える |
| Replatform（lift, tinker, and shift） | 移すときに少し最適化する。 | 自己管理の DB を RDS や Aurora にする |
| Refactor | 移すときにアーキテクチャを変え、クラウドネイティブの機能を使う。 | モノリスをサーバーレス構成に分割する |

### 2. 大規模移行で選ぶ戦略

大規模な移行では、Rehost、Replatform、Relocate、Retire が中心になる。Refactor は移行と同時に近代化するため最も複雑で、多数のアプリをまとめて扱うと管理しきれない。移行後に近代化するほうを勧める。Retain は、移行計画の中で残すアプリを明示するために使う。

### 3. 道具

Rehost の道具は、AWS Transform MGN（旧 AWS Application Migration Service）、AWS Cloud Migration Factory、VM Import/Export である。

データストアの移行には AWS DMS を使う。DMS はリレーショナル DB、データウェアハウス、NoSQL などを移す。オンプレの DB サーバーの棚卸しと移行先の見積もりは Migration Evaluator で行い、DMS Schema Conversion で別エンジン向けにスキーマを変換し、そのうえでデータを移す。CDC（ongoing replication）を使うと、移行中と移行後の変更を継続的に取り込める。

ファイルやデータの転送には AWS DataSync を使う。オンプレや他のクラウドから AWS へ、オンラインで移す。

近代化まで含めた全体の道具は AWS Transform である。エージェント型 AI で、インフラの移行、メインフレームや Windows アプリの変換、技術的負債の解消を担う。MGN も AWS Transform の一部になった。

### 4. 2026年の変更

AWS Application Discovery Service と AWS Migration Hub は、どちらも 2025年11月7日から新規受付を終了した。同等の機能は AWS Transform が提供する。

AWS DMS Fleet Advisor は、2026年5月20日にサポートを終了した。データベースの棚卸しは Migration Evaluator へ移る。

AWS Transform MGN は、2026年10月からエージェントレス複製を新規では提供しなくなった。エージェント型の複製が推奨されている。古い教材の「エージェントレスで始める」は、今の前提と食い違う。

### 5. 進め方（ウェーブとストラングラーフィグ）

移行は波（wave）に分けて進める。まずアプリ間の依存関係をマッピングし、依存の強いものを同じ波に束ねる。依存を無視して個別に移すと、移行後に連携が切れて障害が起きる。

1回で置き換えられないアプリは、ストラングラーフィグパターンを使う。既存アプリの周りに新しい実装を少しずつ足し、機能の移し替えが終わったら古いほうを止める。

## 具体例・コード

社内システム30本を移す前提で、次の6ステップで進める。

1. 棚卸し: 30本の構成、データストア、利用者、依存先を洗い出す。
2. 分類: 各アプリに7Rのどれかを割り当てる。Retire と Retain も判断する。
3. 波に分ける: 依存関係のマップを作り、依存の強いアプリを同じ波にまとめる。
4. 移す: Rehost と Replatform のアプリは MGN や DMS で移し、データは DataSync や CDC で同期する。
5. 検証: 移した後の動作と性能を確認し、切り替える。
6. 移行後に近代化: 安定してから Refactor を進める。1回で置き換えられない既存アプリは、ストラングラーフィグで少しずつ置き換える。

## つまずきポイント

- 「Refactor が最も良い戦略なので、全部それで移す」は間違い。移行と同時の近代化は複雑さが高く、大規模移行には向かない。
- 「Replatform と Rehost は同じ意味」は間違い。Replatform は移すときに少し最適化する点が違う。
- 「DMS はデータを移すだけで、別の DB エンジンへは移せない」は間違い。DMS Schema Conversion でスキーマを変換し、別エンジンへ移せる。
- 「MGN は今もエージェントレス複製で始めればよい」は間違い。2026年10月から新規では提供されず、エージェント型の複製が推奨されている。
- 「Migration Hub と Application Discovery Service は今も新規で使える」は間違い。どちらも 2025年11月7日に新規受付を終え、同等の機能は AWS Transform が提供する。
- 「Retain は移行の失敗を意味する」は間違い。最近更新した、移す事業価値がない、といった理由で意図して残す戦略である。
