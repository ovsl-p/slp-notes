# AWS のコンピューティングサービスの違い

## ひとことで

「どこまで自分で管理するか」と「いつ動くか」の2軸で、サービスが決まる。常時動くならサーバー（EC2）、イベントで動くなら Lambda、コンテナなら ECS か EKS。

## なぜ効くか / どこで使うか

分野1の設問は、ワークロードの性質（常時か、突発的か、長いか短いか、コンテナか）を読んで、動かす場所を選ばせる。コストと運用の手間の両方が判断材料になる。

## 前提となる知識

- 仮想マシン: 1台の物理機械の中に、OS ごと独立した機械を複数動かす仕組み。EC2 はこれを借りる。
- コンテナ: アプリとその依存をひとまとめにした箱。OS の中で隔離して動かす。
- イベント駆動: 出来事（リクエスト、ファイル追加、キューのメッセージ）が来たときだけ処理する。

## 本体の解説

### 1. 管理の範囲で分ける

| 管理の範囲 | サービス | 一言で |
| --- | --- | --- |
| OS まで自分で管理 | EC2 | 仮想サーバーを借りる。最も自由 |
| コンテナだけ管理 | ECS、EKS（+ Fargate） | サーバーを意識せず、コンテナを動かす |
| 関数だけ書く | Lambda | 呼ばれたときだけ、コードを実行する |
| アプリだけ渡す | Elastic Beanstalk | デプロイと管理を任せる。裏は EC2 |

### 2. EC2（仮想サーバー）

EC2 は、インスタンスタイプ（CPU、メモリ、ネットワークの組み合わせ）を選んで起動する。

購入オプションでコストが変わる。

- オンデマンド: 使った分だけ。計画が立たないとき。
- Savings Plans、リザーブドインスタンス: 1年や3年の約束で割引。常に動く分に向く。
- スポットインスタンス: 空いている容量を安く使う。途中で止められることがあるので、途中から再開できる処理に向く。
- 専有ホスト: 物理ホストを占有する。ライセンスの要件などで使う。

プレイスメントグループは、インスタンスの配置を決める。クラスター（近くに置いて、低遅延）、スプレッド（別々のハードウェアに置いて、障害を分ける）、パーティション（ラックを分けて、大規模な分散処理に使う）。

### 3. Auto Scaling（台数を自動で増減）

Auto Scaling は、負荷に合わせて EC2 の台数を増減する。複数の AZ にまたがって台数を配り、ヘルスチェックで異常なインスタンスを置き換える。

- ターゲットトラッキング: CPU 使用率などの目標値を保つ。最も使われる。
- スケジュール: 決まった時間に増やす。
- 予測: 過去のパターンから先に増やす。

ELB と組み合わせると、台数の増減が利用者から見えなくなる。

### 4. Lambda（イベントで実行）

Lambda は、関数を呼び出されたときだけ動かす。サーバーの管理はいらず、実行回数と時間で課金される。

制限を覚えておく。
- 1回の実行は最長15分。長い処理には向かない。
- メモリは128 MB から10 GB まで。CPU はメモリに比例して割り当てられる。
- 同時実行数に上限があり、超えると待たされる。

SQS、S3、EventBridge、API Gateway などから直接呼ばれる。

### 5. ECS と EKS（コンテナの管理）

ECS は AWS 独自のコンテナ管理。EKS は Kubernetes のマネージド版。

違いは、Kubernetes の知識や移植性が必要かどうか。Kubernetes のツールや仕組みを使うなら EKS、AWS の中だけで完結させるなら ECS が、運用は軽くなりやすい。

起動の場所も選べる。
- EC2 上で動かす: 台数を自分で管理する。
- Fargate で動かす: サーバーを意識せず、タスク単位で CPU とメモリを指定する。

### 6. Elastic Beanstalk（アプリを渡す）

Elastic Beanstalk は、アプリのコードを渡すと、EC2、ELB、Auto Scaling を組み立てて動かす。インフラの細かい設定は見えなくなるが、設定を自由に変えるのは難しい。

素早く Web アプリを動かしたい、インフラの知識が少ない、というときに向く。

### 7. 選び方の順番

1. イベントで動き、1回の処理が15分以内 → Lambda
2. コンテナで動かす → ECS（AWS の中で完結）か EKS（Kubernetes が要る）。サーバー管理を避けたいなら Fargate
3. OS の設定やソフトウェアを自由に入れたい → EC2（+ Auto Scaling）
4. 負荷に合わせて増減する → Auto Scaling を組み合わせる
5. コストを下げたい → 常に動く分は Savings Plans、途中で止まっても良い処理はスポット

## 具体例・コード

画像のアップロード処理の例。

1. 画像のアップロードは S3 に置く。イベントが出る
2. サムネイルの作成は Lambda で行う（数秒で終わるので15分の制限に収まる）
3. 動画の変換は時間がかかるので、ECS か Batch のコンテナで行い、スポットを使う
4. Web の API は ECS（Fargate）で動かし、負荷に合わせてタスク数を増やす

## つまずきポイント

- Lambda で長い処理を動かせると思う。1回の実行は最長15分。
- スポットインスタンスは、安定した処理に向くと思う。途中で止められるので、再開できる処理に向く。
- Auto Scaling は、1つの AZ だけで台数を増やすと思う。複数の AZ に配るのが基本。
- Fargate と EKS を同じものだと思う。Fargate は起動の場所、EKS は管理する仕組み。組み合わせて使える。
- Elastic Beanstalk を、細かく設定できる本番向けだと思う。細かい調整は限られる。
