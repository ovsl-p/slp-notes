# 運用を自動で回す道具

## ひとことで

Systems Manager のランブックとパッチ適用、スケジューラ、スケーリング、自動復旧、安全装置で、運用の手作業を減らす。

## なぜ効くか / どこで使うか

運用の手作業は、人が増えない限り速度も正確さも頭打ちになる。手順をランブックに書き、時刻やアラームを引き金にして回せば、同じ操作を毎回同じ形で実行できる。

使う場面は、SSH を開けたくない、パッチを決まった時間帯に当てたい、障害時に人手を介さず直したい、といった条件が出たときだ。

異常の検知側は [[オブザーバビリティの計測と通知]] で扱う。環境を揃える側は [[IaC でインフラを揃える仕組み]] が土台になる。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| ランブック | 運用手順を JSON や YAML で書いたもの。 |
| Automation | ランブックで処理を自動化する Systems Manager の機能。 |
| Run Command | エージェント入りのノードへコマンドを一斉に実行する機能。 |
| Session Manager | 踏み台なしでシェルに入る機能。 |
| パッチベースライン | どのパッチを当てるかを決める規則。 |
| メンテナンスウィンドウ | 作業を実行してよい時間帯。 |
| DLQ | 処理に失敗したメッセージの送り先キュー。 |
| Service Quotas | サービスごとの上限を確認し、引き上げを申請する仕組み。 |

## 本体の解説

### 1. Systems Manager のランブックとリモート操作

Systems Manager は運用タスクの道具箱である。中でも Automation は、ランブックで手順を自動化する。EC2、RDS、S3 など複数のサービスをまたぐ手順を組める。

ランブックには、承認待ち、分岐、待機を挟める。決まった時刻に回すこともできる。

リモート操作には2つの道具がある。Run Command は、エージェントの入ったノードに対してコマンドを一斉に実行する。Session Manager は、踏み台サーバなしでシェルに入る。

どちらもインバウンドのポートを開けずに済む。マネージドノードには、エージェント、IAM 権限、SSM エンドポイントへの外向き HTTPS が要る。IAM 権限は、EC2 ならインスタンスプロファイルかデフォルトホスト管理設定（DHMC）、オンプレのサーバーならハイブリッドアクティベーションで与える。Session Manager なら、シェル操作の記録も残せる。

### 2. パッチ適用とメンテナンスウィンドウ

Patch Manager の代表的な組み方は、パッチベースラインで当てる中身を決め、メンテナンスウィンドウで実行してよい時間帯を決める。Quick Setup のパッチポリシーなら、この2つをまとめて設定できる。

Patch Manager は準拠状態も評価する。非準拠のノードは、評価の結果をもとにパッチを当てて直せる。

### 3. スケジューラとスケーリング

EventBridge Scheduler は、サーバーレスのスケジューラである。cron 式と rate 式で繰り返しを組め、1回だけの実行も指定できる。

実行の時間枠を柔軟に決められ、270以上のサービスを呼び出せる。自前でインフラを持つ必要はない。

スケーリングの方式は、動的・スケジュール・予測の3つに分かれる。動的スケーリングには、ターゲット追跡、ステップ、シンプルの3種類がある。

| 方式 | 動き |
|---|---|
| ターゲット追跡 | 指標を目標値に保つ |
| ステップ | しきい値を超えた量に応じて段階的に増減する |
| シンプル | 1つのしきい値で決まった数だけ増減する |
| スケジュール | 予測できる負荷の山に合わせる |
| 予測スケーリング | 過去のパターンから先回りする |

コンピューティングごとの違いは [[コンピューティングサービスの違い]] にある。

### 4. 自動復旧と安全装置

自動復旧は、ヘルスチェックと入れ替えで組む。Auto Scaling は不健全なインスタンスを入れ替える。ECS はタスクを入れ替える。

Lambda の非同期呼び出しは、関数がエラーを返すと既定で2回まで自動で再試行する。それでも失敗したイベントは、DLQ か失敗時の送信先（on-failure destination）を設定していれば退避でき、後から調べて再処理できる。設定がなければ捨てられる。

自動化は暴走すると被害を広げる。そこで、次の4つの安全装置を置く。

| 安全装置 | 役割 |
|---|---|
| サーキットブレーカー | 失敗が続いたら呼び出しを止める |
| レート制限 | 流量の上限を決める |
| バルクヘッド | 機能ごとに隔離して被害を広げない |
| 指数バックオフ付きの再試行 | 待ち時間を倍にしながらやり直す |

サービスごとの上限にも注意が要る。上限に当たるとスケールもデプロイもできないので、Service Quotas で確認し、必要なら引き上げを申請する。

障害時の切り替えは [[災害対策の4つの型と切り替えの道具]] で扱う。

## 具体例・コード

自動修復は、CloudWatch アラームから EventBridge を経由して、Systems Manager の Automation を呼ぶ形で組める。

```text
CloudWatch アラーム（異常を検知）
  -> EventBridge（アラームの状態変化を受ける）
    -> Systems Manager Automation（ランブックを実行）
         1. 承認待ち（必要な場合だけ）
         2. 分岐（対象の状態で処理を分ける）
         3. 待機（復旧を待つ）
```

アラームでランブックを起動する流れなら、検知から修復までに人の操作が入らない。EventBridge のルールのロールには StartAutomationExecution の権限を、ランブックには AutomationAssumeRole を渡す。承認待ちを挟めば、人の確認を残すこともできる。

## つまずきポイント

- 「Run Command を使うには SSH のポートを開ける必要がある」は間違い。SSH のポートは不要である。マネージドノードには、エージェント、IAM 権限、外向き HTTPS を用意する。
- 「Session Manager を使うには踏み台サーバが要る」は間違い。踏み台なしでシェルに入れ、インバウンドのポートも開けない。操作の記録も残せる。ノード側の前提は Run Command と同じである。
- 「EventBridge Scheduler は繰り返しの実行専用である」は間違い。cron 式と rate 式の繰り返しに加えて、1回だけの実行も指定できる。
- 「予測スケーリングとスケジュールは同じ仕組みである」は間違い。スケジュールは予測できる負荷の山に合わせ、予測スケーリングは過去のパターンから先回りする。
- 「Lambda の非同期呼び出しは、失敗するとそこで終わる」は間違い。既定で2回まで自動で再試行する。DLQ か失敗時の送信先を設定していれば退避でき、なければ捨てられる。
- 「スケーリングを自動にすれば、上限は気にしなくてよい」は間違い。上限に当たると、スケールもデプロイもできない。Service Quotas で確認し、必要なら引き上げを申請する。
