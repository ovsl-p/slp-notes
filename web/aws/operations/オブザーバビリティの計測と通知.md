# オブザーバビリティの計測と通知

## ひとことで

メトリクス、ログ、トレースを集めて状態を見えるようにし、アラームから自動修復へつなぐ仕組みである。

## なぜ効くか / どこで使うか

3種のテレメトリ（監視用の計測データ）を一か所で扱うと、障害の原因をたどる時間が短くなる。アラームを EventBridge から Systems Manager の Automation へ、または SNS から Lambda へ結べば、検知から修復までを自動で回せる。

使う場面は次のとおりだ。

- EC2 や ECS、EKS で動くワークロードの状態監視
- 複数アカウントにまたがるログとメトリクスの集約
- Bedrock や SageMaker を使う AI/ML ワークロードの品質確認
- 検知後の自動修復と、監視コストの抑制

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| メトリクス | 数値の時系列データ。 |
| ログ | イベントの記録。CloudWatch Logs に集める。 |
| トレース | 1リクエストの流れの記録。X-Ray で扱う。 |
| ロググループ | ログストリームをまとめる単位。 |
| SNS トピック | アラームの通知先になる配信口。 |
| ADOT | AWS Distro for OpenTelemetry。OpenTelemetry 標準の収集ツール。 |

## 本体の解説

### 1. 3つのテレメトリと各サービスの分担

CloudWatch は、リソースとアプリをリアルタイムに監視する。メトリクス、アラーム、ダッシュボード、ログ、トレースを一か所で扱える。

メトリクスには標準とカスタムがある。標準メトリクスはサービスが自動で出し、カスタムメトリクスは自分で出す。メトリクスフィルタを使うと、ログから数値を作れる。

ログはロググループとストリームで整理する。保持期間を設定しないと、ログが消えずに保管され続ける。

トレースは X-Ray が担う。セグメントとサブセグメントで、1リクエストの流れを追う。X-Ray の計装（計測コードの組み込み）は、コードを書かずに設定だけで済む場面が多い。

OpenTelemetry の標準を使うなら、ADOT でメトリクスとトレースを集め、CloudWatch や X-Ray へ送る。ベンダーに依存しない計装にしたいときに選ぶ。

X-Ray の SDK とデーモンは、2026年2月25日に保守モードへ入り、以後はセキュリティ修正だけになる。全サポートの終了は2027年2月25日と告知されていたが、公式のタイムラインでは終了日が N/A になっている。計装の側は ADOT（OpenTelemetry）へ移す。送り先としての X-Ray はそのまま使える。

EC2 では CloudWatch エージェントを入れる。標準メトリクスに含まれないメモリやディスクの使用率は、このエージェントで取る。

### 2. コンテナの監視

Container Insights は、ECS、EKS、Kubernetes on EC2 のメトリクスとログを集めて可視化する。ECS と EKS の Fargate にも対応する。

EKS では、CloudWatch Observability のアドオンか Helm チャートを入れる。ノードごとに CloudWatch エージェントと Fluent Bit が動く。コンピューティングの選択は [[コンピューティングサービスの違い]] で扱う。

### 3. 複数アカウントのログ集約とアーカイブ

クロスアカウントの観測は、同じリージョン内で使う。監視アカウント（見る側）とソースアカウント（データを出す側）をリンクする。リンクすると、監視アカウントからメトリクス、ログ、トレースをまとめて見られる。データを全部1か所へ集めなくてよい。アカウント構成の考え方は [[マルチアカウントのガバナンス]] にある。

ログを他へ流す方法は2つある。

| 方法 | 流し先 | 性質 |
|---|---|---|
| サブスクリプションフィルタ | Lambda、Kinesis、Firehose など | リアルタイムに流す |
| S3 へのエクスポート | S3 | ライフサイクルで安い階層へ移せる |

### 4. 通知と自動修復

アラームは、メトリクスのしきい値で状態を変える。複合アラームは、複数のアラームの状態をまとめて1つにする。

アラームのアクションの代表は、SNS トピックへの通知である。ほかに Lambda の直接呼び出し、EC2 と Auto Scaling のアクション、OpsItem の作成がある。インシデントの作成は Incident Manager の機能で、新規の受け付けは2025年11月7日に終わっている。自動修復まで組むときは、アラームの状態変化を EventBridge のルールで受け、Systems Manager の Automation を起動する。SNS から Lambda を呼び、Lambda が Automation を起動する形でもよい。経路の組み立ては [[運用を自動で回す道具]] にある。検知と監査の線引きは [[検知と監査の違い]] にある。

### 5. AI/ML ワークロードの計測

Bedrock では、呼び出し回数、レイテンシ、スロットリングのメトリクスを見る。SageMaker では、データの分布のずれ（ドリフト）を Model Monitor で検知する。

AI エージェントは、CloudWatch Omni で振る舞いを追う。Omni は、テレメトリからサービスと依存関係を見つけ、自然言語の質問からクエリを作る機能である。2026年9月に一般提供が始まり、バージニア北部、オレゴン、アイルランドの3リージョンで使える。サービス全体の選び分けは [[AI サービスの使い分け]] にある。

### 6. 費用

費用は、カスタムメトリクスの数、ログの取り込み量と保管量、アラームの数で変わる。ログの取り込みは量に応じて課金されるので、不要なログを減らすと費用を抑えられる。

## 具体例・コード

EC2 のメモリ使用率でアラームを鳴らし、自動で直す流れを組む。

1. CloudWatch エージェントを EC2 に入れ、メモリ使用率をカスタムメトリクスとして出す
2. メモリ使用率のしきい値でアラームを作り、評価期間を決める。人へ知らせるだけなら、アクションに SNS トピックを指定する
3. アラームの状態変化を EventBridge のルールで受け、Systems Manager の Automation を起動して直す。ルールのロールには Automation を起動する権限（StartAutomationExecution）を与え、ランブックは AutomationAssumeRole で実行ロールを引き受ける

複数アカウントのログは、監視アカウントにリンクして一か所で見る。長期保管するログは、S3 へエクスポートしてライフサイクルで安い階層へ移す。

## つまずきポイント

- 「EC2 のメモリ使用率は標準メトリクスで見える」は間違い。標準メトリクスには含まれず、CloudWatch エージェントを入れて取る。
- 「ログは放置しても費用は増えない」は間違い。保持期間を設定しないと、保管が延び続けて費用が積み上がる。
- 「ADOT は X-Ray の代わりに使うものだ」は間違い。収集の層では ADOT が X-Ray SDK とデーモンの後継になるが、送り先としての X-Ray と CloudWatch はそのまま使う。
- 「複数アカウントを見るには、ログを1アカウントへ全部集める必要がある」は間違い。同じリージョン内なら、監視アカウントとソースアカウントをリンクして、ログを複製せずに横断で見られる。
- 「アラームは通知するだけの機能だ」は間違い。Lambda を直接呼んだり、OpsItem を作ったりもできる。EventBridge 経由で Systems Manager の Automation を起動すれば、自動修復につながる。
- 「ログのコストは保管量だけで決まる」は間違い。取り込み量にも比例するので、不要なログを減らすのが効く。
