# コストの配分と可視化

## ひとことで

コスト配分は、タグとコスト分類で支出の持ち主を決め、CUR 2.0 で集計し、Budgets と異常検知で通知する仕組みである。説明できる粒度は、タグの設計と按分の方法で決まる。

## なぜ効くか / どこで使うか

EC2、Aurora、Route 53、ECS は複数のチームで共有されることが多い。請求書の合計だけでは、どのチームがどれだけ使ったかが分からない。タグで利用者の情報を付け、請求データに出して集計すると、部門ごとに金額を説明できる。

使うのは、月末の部門別の費用説明、部門への請求（チャージバック）、金額の見える化（ショーバック）、予算超過の早期通知、想定外の支出の検知である。

## 本体の解説

### 1. タグ設計

タグは配分の最小単位である。キーを決め、値の付け方を揃えることが設計の出発点になる。

ユーザー定義のタグは、有効化しない限り請求レポートに出ない。タグキーを有効化すると、同じキーを持つすべての値に効く。有効化してからコストデータに現れるまで最大24時間かかるため、設定直後の確認は反映前になることがある。

### 2. 強制の手段

タグの付け忘れを防ぐ手段は3つある。

- タグポリシー: 付け方の標準化に使う。キーと値の大文字小文字を揃える。
- SCP: 権限の条件として、タグの付与を求める。リソース作成の時点で働く。効くのはメンバーアカウントのプリンシパルだけで、管理アカウントのユーザーとロール、サービスリンクロールには効かない。作成時にタグを要求できるのは、作成 API が `aws:RequestTag` に対応しているリソースに限られる。
- AWS Config ルール: 設定を評価し、タグの有無を確認する。作成後の状態を見る。

SCP は権限の条件、Config は設定の評価であり、役割が異なる。両者を組み合わせると、作成時の拒否と作成後の検出を分担できる。

### 3. 集計の道具

集計には、Cost Explorer、CUR 2.0、Cost Categories、按分データの4つを使い分ける。

CUR 2.0 は Data Exports から作る。SQL で必要な列を選び、行を絞り、列名を変える。不要な列を落とせるので、下流の集計や BI ツールに渡すデータの形を、作成時に決められる。

Cost Categories は、ルールでコストを組織構造に割り当てる。割り当て結果は CUR の列として出る。タグが付いていないコストも、アカウントの所属で部門に寄せられる。

按分データは、ECS のタスクと Kubernetes の Pod というコンテナ単位のコストを CUR に追加する。EC2 インスタンスの按分コストを基に、コンテナが使った CPU とメモリの割合から計算する。共有クラスターの部門配分に使える。

### 4. 運用（予算と異常検知）

Budgets は、コストと使用量を追跡し、実績と予測の両方で通知する。しきい値に達したときに IAM ポリシーを適用するなどのアクションを設定できる。例として、追加リソースの作成を拒否する設定が可能である。Budgets のアクションを使うと、通知だけでは止まらない支出を自動で抑えられる。

Cost Anomaly Detection は、機械学習で異常な支出を検出する。通知はメールか SNS で届く。原因は、サービス、アカウント、リージョン、使用タイプの4次元で示され、金額影響の大きい順に並ぶ。どこから調べるかの起点が得られる。

### 5. チャージバックとショーバック

チャージバックは、部門に実際に請求を回す。ショーバックは、金額を見せて認識させるが、請求は回さない。

チャージバックとショーバックは、同じ集計結果を使える。違うのは、Cost Categories の割り当てや按分後の数値を、実際の請求に使うか、報告にとどめるかである。請求に使うかどうかは、社内の合意で決める。

## 具体例・コード

3つのチーム（Team1、Team2、Team3）が同じ組織で AWS を使う場合を例にする。

1. タグのキーと値のルールを決める。キーは部門を表すものを1つにし、値の大文字小文字を揃える。
2. タグポリシーで、キーと値の付け方を組織全体に適用する。
3. SCP または Config ルールで、タグの付与を強制する。作成時の拒否と作成後の検出を分担する。
4. コスト配分タグを有効化する。有効化後、コストデータに現れるまで最大24時間待つ。
5. Cost Categories を作る。アカウント1〜3 を Team1、アカウント4〜5 を Team2、残りを Team3 に割り当てる。結果は CUR の列として出る。
6. Data Exports で CUR 2.0 を作り、ECS の按分データを含める。月末に、Team ごとの金額を集計する。

集計の SQL は次の形になる。列名は実際の CUR 2.0 のスキーマに従うため、以下は構造だけを示す擬似コードである。

```sql
-- 擬似コード。<列名> は実スキーマの列に置き換える
SELECT <部門列>, <サービス列>, SUM(<金額列>) AS 合計
FROM <CUR 2.0 のテーブル>
WHERE <期間の条件>
GROUP BY <部門列>, <サービス列>
```

## つまずきポイント

- 「タグを付ければ、すぐに請求レポートに出る」は間違い。ユーザー定義のタグは有効化が必要で、有効化後も最大24時間かかる。
- 「タグキーを有効化すると、そのキーの一部の値だけに効く」は間違い。同じキーを持つすべての値に効く。
- 「SCP で権限を制限すれば、AWS Config ルールは不要」は間違い。SCP は権限の条件、Config は設定の評価で、役割が異なる。
- 「CUR 2.0 は列が固定で、減らせない」は間違い。SQL で列を選び、行を絞り、列名を変えて出力スキーマを制御できる。
- 「ECS のコストは EC2 の課金にそのまま含まれるため、按分は不要」は間違い。按分データを有効にすると、EC2 の按分コストをもとに、コンテナの CPU とメモリの割合でタスクと Pod に配る。
- 「異常検知は、設定した金額を超えたら通知する」は間違い。機械学習で異常な支出を検出し、原因を4次元で示す。
