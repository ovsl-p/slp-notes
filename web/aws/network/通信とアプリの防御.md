# 通信とアプリの防御

## ひとことで

AWS で通信を守る仕組みは5つあり、守る層の違いで見分ける。

## なぜ効くか / どこで使うか

攻撃には、Web アプリの中身を狙うものと、大量のトラフィックで対象を埋めるものがある。層に合わない仕組みを選ぶと、攻撃は防げない。

使う場面は、公開 Web アプリの前段、VPC 内の通信の検査、リソース単位の許可設定などだ。

## 前提となる知識

| 用語 | 一言の説明 |
|---|---|
| ステートフル | 通信の状態を覚え、戻りの通信を自動で判断する。 |
| ステートレス | 通信の状態を覚えず、通過するパケットを個別に判断する。 |
| CIDR | IP アドレスの範囲を `10.0.0.0/16` のような表記で表す。 |
| ポート | 同じ IP アドレスの中で、通信の行き先のサービスを分ける。 |
| DDoS | 大量のリクエストやパケットで対象を過負荷にする。 |
| L3/L4、L7 | 層を番号で示す。L3/L4 はネットワークとトランスポート、L7 は HTTP などのアプリケーションの層。 |

VPC の基礎は [[VPC の前提知識]] にある。

## 本体の解説

### 1. 守る層で分ける

| 層 | サービス | 役割 |
|---|---|---|
| L3/L4（ネットワーク、トランスポート） | Shield Standard、Shield Advanced | 大量のパケットによる DDoS を防ぐ |
| L7（HTTP の中身） | WAF | リクエストの内容を Web ACL のルールで検査する |
| VPC 内の通信 | Network Firewall | VPC を通る通信の中身をルールで検査する |
| EC2 などのリソース単位 | セキュリティグループ | ENI 単位で通信を許可する |
| サブネット単位 | NACL | サブネットの出入りを許可と拒否で制御する |

### 2. WAF

WAF は HTTP(S) のリクエストを検査するサービス。検査には Web ACL を使う。Web ACL は、ルールを集めたもの。

ルールに一致したリクエストは、許可、遮断、カウントのいずれかで処理する。CAPTCHA やチャレンジを出すこともできる。

WAF は CloudFront、ALB、API Gateway の前に付けて使う。ルールは自作のほか、AWS マネージドルールグループ（既成の攻撃パターン）を使える。ルールの容量は WCU という単位で管理する。

### 3. Shield

Shield Standard は、全利用者に自動で付く。追加料金はかからない。ネットワーク層とトランスポート層（L3/L4）の DDoS を防ぐ。

Shield Advanced は有料のサブスクリプション。L7 の DDoS 対策を含む。L7 の自動緩和は、保護するリソースに Web ACL を関連付けて使う。Shield Advanced は専用のルールグループを Web ACL に追加する。追加されるのは、既知の攻撃元に対するレートベースルール（ShieldKnownOffenderIPRateBasedRule）と、攻撃の特徴から作ったルールである。どちらも動作は Count か Block から選べる。ほかに、DDoS 対応チームへの相談や、攻撃による料金の補償がある。

### 4. Network Firewall

Network Firewall は VPC の中の通信を検査するファイアウォール。サブネットに置いたエンドポイントを経由させるよう、ルートテーブルで向ける。

ルールエンジンは、ステートレスとステートフルの2種類がある。ステートフルでは、ドメイン名での許可や拒否と、Suricata 形式の IPS ルールを書ける。

VPC をまたいで集中的に検査する場合は、Transit Gateway 経由の構成にする。

#### Network Firewall はどんな攻撃を防ぐのか

VPC から外へ出ていく通信を見張り、マルウェアの配布元や攻撃者のサーバーへの接続を止めるのが役割である。ルールで既知の攻撃パターンを検知して遮断することもできる。セキュリティグループや NACL は IP とポートで判断するだけなので、通信の中身やドメイン名までは見られない。

#### 通信の中身とは、パケットのどこまでか

見るのは、ヘッダーにある IP アドレスとポート、そしてデータ部分に含まれる文字列の両方である。ドメイン名はヘッダーには入っていない。TLS の ClientHello にある SNI、HTTP の Host ヘッダー、DNS の問い合わせといったデータ部分から読む。

HTTPS は暗号化されているので、既定では本文まで読めない。読めるのは SNI までで、そこでの許可や拒否になる。TLS 検査の設定を入れると、ACM の証明書で復号し、復号した本文をステートフルルールで検査してから再暗号化する。

### 5. セキュリティグループと NACL の違い

| 項目 | セキュリティグループ | NACL |
|---|---|---|
| 適用単位 | EC2 などのリソース（ENI） | サブネット |
| 状態の扱い | ステートフル | ステートレス |
| 書けるルール | 許可のみ | 許可と拒否 |
| 戻りの通信 | 自動で許可 | 明示的な許可が必要 |
| 評価の方法 | すべてのルールを評価する | 番号の小さい順に評価し、最初に一致したもので決まる |

通信は、セキュリティグループと NACL の両方で許可される必要がある。NACL が拒否した通信は、セキュリティグループが許可していても止まる。

## 具体例・コード

Web アプリ1つを例に、通信の流れと防御を整理する。

1. ユーザーのリクエストは CloudFront に届く。WAF の Web ACL を CloudFront に付け、マネージドルールで既知の攻撃を遮断する
2. CloudFront から ALB へ転送される。Shield Standard は、この経路の L3/L4 の DDoS を自動で防ぐ
3. ALB のセキュリティグループは、送信元を CloudFront のオリジン向けマネージドプレフィックスリスト（com.amazonaws.global.cloudfront.origin-facing）に限定する。このリストはルール数の上限を 55 消費する。既定の上限は 60 なので、残りは5になる。経路をさらに絞るなら、CloudFront が付けるカスタムヘッダーを ALB のリスナールールで検査する
4. アプリの EC2 のセキュリティグループは、ALB のセキュリティグループを参照して、ALB からの通信だけを許可する

```
app-sg  inbound: TCP 8080, source = alb-sg
```

5. プライベートサブネットの NACL は、ステートレスなので、戻りの通信も明示的に許可しておく。外部 API への外向き通信は、Network Firewall で検査する

## つまずきポイント

- 「Shield Advanced を入れれば DDoS をすべて防げる」は間違い。L7 の自動緩和には、保護するリソースへの Web ACL の関連付けが要る。
- 「WAF は EC2 に直接付けられる」は間違い。WAF は CloudFront、ALB、API Gateway などの前に付ける。
- 「Network Firewall はすべての通信を自動で検査する」は間違い。ルートテーブルで経由させたサブネットの通信だけが対象になる。
- 「セキュリティグループで拒否のルールを書ける」は間違い。セキュリティグループは許可のみで、拒否は NACL で書く。
- 「Shield Standard は契約して申し込む必要がある」は間違い。Shield Standard は全利用者に自動で付き、追加料金もかからない。
