# VPC とネットワークの基礎

## ひとことで

VPC はリージョン内に切った仮想ネットワークで、通信できるかどうかは「経路があるか（ルートテーブル）」と「フィルタで許可されているか（セキュリティグループとネットワーク ACL）」で決まる。

## なぜ効くか / どこで使うか

AWS 上のシステムは、ほとんどが VPC の上で動く。構成を決めるときも障害を調べるときも、サブネットの切り方、経路の通し方、外部から届くかどうかを判断するには、この基礎が欠かせない。

コンテナや Kubernetes を使う場合も、EKS（標準の VPC CNI）では Pod に VPC の IP がそのまま振られるので、VPC のネットワークの理解が曖昧だと、Pod の IP がどこから届くのかが分からず、Service や Ingress の経路も追えない。

## 前提となる知識

IP アドレスと CIDR、ルーティング、NAT、DNS の基礎は [[VPC の前提知識]] にまとめた。先にそちらを読んでおく前提で書いている。

| 用語 | 一言の説明 |
|---|---|
| IP アドレスと CIDR | アドレスの範囲を表す書き方。VPC とサブネットの範囲を決める。接続先と範囲が重複すると経路を通せない。 |
| ルーティング | 「どこ宛のパケットをどこへ送るか」を決める表。VPC の要。 |
| NAT の考え方 | プライベートな IP のまま外に出る仕組み。 |
| DNS の基礎 | 名前から IP を引く仕組み。VPC の中にも用意されている（[[DNS と名前解決]]）。 |

## 本体の解説

![[assets/web/vpc-subnet-routing.svg]]

### 1. VPC とサブネット

VPC はリージョン内に1つ以上の CIDR ブロックで作る仮想ネットワークで、その中をサブネットで区切る。

サブネットは AZ（アベイラビリティゾーン）に紐づく。1つのサブネットが複数の AZ にまたがることはないので、冗長化するなら AZ の数だけサブネットを作る。

パブリックとプライベートの違いは名前ではなく経路で決まる。サブネットのルートテーブルにインターネットゲートウェイへの経路があればパブリックで、なければプライベートとなる。

### 2. ルートテーブル

ルートテーブルはサブネットに関連付ける。行は「宛先 CIDR」と「ターゲット（IGW、NAT ゲートウェイ、Transit Gateway、VPC ピアリングなど）」の組で書く。

VPC 内の通信はローカルルートで自動的に通る。それ以外の宛先は、明示的に足さないと通らない。逆に言えば、足し忘れが「つながらない」の大半を占める。

同じ VPC の中でも、サブネットごとに別のルートテーブルを当てられる。片方のサブネットだけ外部に出せる構成は、このルートテーブルの分け方で作る。

### 3. 外とつなぐための装置

| 装置 | 役割 | 置き場所 |
|---|---|---|
| インターネットゲートウェイ | パブリックサブネットと外部をつなぐ | VPC に1つ |
| NAT ゲートウェイ | プライベートサブネットから外への通信を中継する（送信元 IP は NAT のものになる。外からの通信開始は不可） | ゾーン型はパブリックサブネットに AZ ごと、リージョン型は VPC に1つ |
| VPC エンドポイント | AWS のサービスへ、インターネットを経由せずに届く | ゲートウェイ型はルートテーブル、インターフェイス型はサブネット内の ENI |

従来のゾーン型 NAT ゲートウェイは1つの AZ の中にしか存在しない。1つだけ置くと、他の AZ のサブネットもその NAT を経路に使うため、その AZ が落ちたときに外への通信が止まる。そこで AZ ごとに置き、ルートテーブルも AZ ごとに分ける。

2025年11月からは、リージョン型（Regional NAT Gateway）も選べる。VPC に1つ作れば、ワークロードがある AZ に自動で広がるので、AZ ごとに作る手間とパブリックサブネットが要らなくなる。ただしプライベート NAT（インターネットに出ない NAT）には使えず、その用途ではゾーン型を使い続ける。

VPC エンドポイントには2種類ある。ゲートウェイ型は S3 と DynamoDB 向けで、ルートテーブルに経路を足して使う。インターフェイス型は ENI を作る方式で、セキュリティグループが効く。PrivateLink はこのインターフェイス型の仕組みを使っている。

### 4. 通信を絞る2段

セキュリティグループはインスタンス（ENI）単位で、ステートフル（戻りの通信は自動で許可）で、許可ルールしか書けない。

ネットワーク ACL はサブネット単位で、ステートレス（戻りも明示的に許可する）で、拒否ルールも書ける。

実務では、細かい許可はセキュリティグループで設定し、ネットワーク ACL は「この IP 範囲は丸ごと拒否」のような粗い制御に使う分担が一般的だ。

ACL のルールは番号の小さい順に評価され、最初に一致したルールで許可か拒否が決まる。そのため、広い許可を小さい番号に置くと、後ろに書いた拒否は効かない。

### 5. DNS と VPC

VPC の Route 53 Resolver は、CIDR の先頭アドレスに +2 したアドレス（10.0.0.0/16 なら 10.0.0.2）で動く。+1 は VPC のルーター用で、DNS ではない。この Resolver は VPC の中からしか使えない。

詳細は [[DNS と名前解決]] に分けた。

### 6. 料金で効くところ

NAT ゲートウェイには、時間あたりの料金と、処理したデータ量あたりの料金がかかる。別の AZ にあるリソースとの通信にも、データ転送料金がかかる。

コストを下げたいときは、まず NAT を通るデータを減らせないかを疑う（S3 や DynamoDB 宛てはゲートウェイ型エンドポイントに逃がす、など）。次に、AZ を跨ぐ通信を減らせないかを見る。

## 具体例・コード

最小の構成を組み立てるときの順番。

1. VPC の CIDR を決める（例: 10.0.0.0/16）
2. AZ の数だけパブリックとプライベートのサブネットを切る（例: /24 ずつ）
3. パブリック側のルートテーブルに `0.0.0.0/0 → IGW` を入れる
4. プライベート側に `0.0.0.0/0 → NAT ゲートウェイ` を入れる（ゾーン型なら、同じ AZ の NAT を向ける）
5. セキュリティグループで、必要なポートだけ許可する

## つまずきポイント

- 「パブリックサブネットという名前を付ければ外部に出られる」は間違い。決めているのはルートテーブル。
- 「ネットワーク ACL はステートフルだ」は間違い。戻りの通信も明示的に許可しないと落ちる。
- 「ゾーン型の NAT ゲートウェイを1つ置けば冗長化できる」は間違い。その AZ の障害で全体が止まる。
- 「CIDR が重複した VPC 同士もつなげる」は間違い。ピアリングでも Transit Gateway でも、重複した範囲には経路を通せない。
- 「エンドポイントはタダで速くなるものだ」は間違い。ゲートウェイ型は無料だが、インターフェイス型は AZ ごとの時間課金とデータ処理料金がかかる。
