# AWS のデータベースサービスの違い

## ひとことで

データの形（表かキーバリューか）と、読み書きの性質（速さ・一貫性・分析か）で、サービスが決まる。

## なぜ効くか / どこで使うか

分野1で出るデータベースの設問は、「どれを選ぶか」と「どの構成で壊れにくくするか」の2つ。形と目的から絞り、可用性と読み取りの拡張を別々に考えると、消去法で答えが出る。

## 前提となる知識

- リレーショナル: 表とキーで関係を持つ。複数の更新をまとめて（トランザクション）扱える。
- キーバリュー: キーで1件を素早く取り出す。関係を持たせない代わりに、拡張しやすい。
- キャッシュ: 同じ読み取りを速く返すための、メモリ上の保管場所。元のデータベースは別にある。

## 本体の解説

### 1. 形と目的で分ける

| 目的 | サービス | 一言で |
| --- | --- | --- |
| 表の関係を保つ業務システム | RDS、Aurora | 既存の SQL エンジンをマネージドで使う |
| 大量の読み書きを安定して返す | DynamoDB | キーで1件を引く、サーバーレスの NoSQL |
| 読み取りを速くする | ElastiCache | 元の DB の前に置く、メモリ上のキャッシュ |
| 大量データを集計する | Redshift | 列指向の分析用データウェアハウス |

### 2. RDS（管理された既存のエンジン）

MySQL、PostgreSQL、MariaDB、Oracle、SQL Server などを、AWS が運用をまかなう形で使う。OS のパッチやバックアップは AWS 側で行う。

可用性は**マルチ AZ**で上げる。マルチ AZ は、別の AZ に同期の待機系を置いて、障害時に切り替える仕組み。待機系は通常は読み取りに使えない。読み取りを増やすなら**リードレプリカ**を使う。リードレプリカは非同期で複製されるので、わずかに遅れて読める。

「障害で止まらないこと」はマルチ AZ、「読み取りが増えて遅いこと」はリードレプリカ、と目的で分けて覚える。

### 3. Aurora（クラウド向けに作り直した RDS 互換）

Aurora は MySQL と PostgreSQL に互換の DB。ストレージは3つの AZ に分散されて、複数のコピーを持つ。障害時は、読み取り用の複製（最大15）の中から新しい書き込み先を選んで、切り替えが速い。

- 読み取りを増やすなら、Aurora レプリカ。ストレージを共有するので、複製の遅れが小さい。
- 負荷が上下するなら、Aurora Serverless。容量を自動で増減する。
- 別のリージョンで低遅延に読みたい、障害時にすぐ切り替えたいなら、Aurora グローバルデータベース。

### 4. DynamoDB（サーバーレスのキーバリュー）

DynamoDB はキーで1件を素早く取り出す NoSQL。容量の管理を意識せず、大量の読み書きに耐える。

設計で一番大事なのは、パーティションキーの選び方。キーが偏ると、一部のパーティションに負荷が集中して遅くなる（ホットパーティション）。複数の条件で引きたいなら、グローバルセカンダリインデックス（GSI）を追加する。

複数リージョンで書き込みたいなら、グローバルテーブル。既定のモード（MREC）は、リージョンをまたいだ複製が非同期で、数秒の遅れが出る。マルチリージョンで強い整合性が要るなら、作成時に MRSC を選ぶ（3リージョン構成が要る）。

### 5. ElastiCache（キャッシュ）

ElastiCache は Valkey、Redis OSS、Memcached のマネージド版。元の DB の前に置いて、同じ読み取りを速く返す。

- Valkey / Redis OSS: 複製や永続化があり、データ構造も扱える。セッション管理やランキングにも使う。
- Memcached: 単純なキャッシュ。複製は無い。

キャッシュは元のデータの代わりにはならない。キャッシュが消えても、元の DB から再び読み直せる構成にする。

### 6. Redshift（分析）

Redshift は列指向の分析用データウェアハウス。大量の行を集計するのが得意で、1行の更新を速く繰り返す業務システムには向かない。

Redshift Spectrum を使うと、S3 にあるデータを取り込まずに問い合わせられる。

### 7. 選び方の順番

1. 表の関係と複数の更新（トランザクション）が要る → RDS か Aurora
2. キーで1件を引く、規模が大きい、サーバーを意識したくない → DynamoDB
3. 同じ読み取りを速くしたい → ElastiCache（元の DB は別に残す）
4. 大量の集計や分析 → Redshift

## 具体例・コード

オンラインストアの例。

1. 注文や決済は、トランザクションが要るので Aurora（マルチ AZ 相当の構成）
2. 商品の閲覧履歴は、キーで引くので DynamoDB
3. 商品カタログの読み取りは、ElastiCache で受けて、元の Aurora は書き込みに集中させる
4. 売上の月次集計は、Redshift に流して分析する

## つまずきポイント

- リードレプリカで可用性が上がると思う。読み取りを増やす仕組みで、障害時の切り替えはマルチ AZ が担う。
- マルチ AZ の待機系から読めると思う。標準の構成では読めない。
- DynamoDB は何でもキーで引けると思う。キーに合わない条件での検索は遅い、または GSI が要る。
- ElastiCache を、データの保管場所だと思う。キャッシュは消えることを前提にする。
- Redshift を、業務の更新に使えると思う。分析向けで、1行ずつの更新には向かない。
