# AWS の暗号化と秘密情報の管理

## ひとことで

データは鍵で守り、鍵は誰がどこで管理するかで選ぶ。パスワードや API キーは、暗号化して保管し、自動で入れ替える仕組みに預ける。

## なぜ効くか / どこで使うか

分野2の設問は、「鍵を誰が持つか」「どこまで自分の管理下に置くか」「法令の要件を満たすか」を問う。サービスの名前より、管理の主体で分けると答えが出やすい。

## 前提となる知識

- 保存時の暗号化: ディスクやバケットに置いたデータを、鍵で暗号化する。
- 通信時の暗号化: TLS で、経路を流れる間を暗号化する。
- 鍵の管理: 鍵を作る、使わせる、入れ替える、消す。この4つを誰が担うかが論点。
- エンベロープ暗号化: データは「データキー」で暗号化し、そのデータキーを「マスターキー」で包む二段構え。大きなデータも速く扱え、マスターキーは外に出ない。

## 本体の解説

### 1. 管理の主体で分ける

| 欲しいもの | サービス | 一言で |
| --- | --- | --- |
| 鍵を AWS の仕組みで安全に管理したい | KMS | 暗号鍵を作り、使用を IAM とキーポリシーで制御する |
| 鍵を自分だけが占有したい、専用の HSM が要る | CloudHSM | 専用のハードウェアで、鍵を利用者の管理下に置く |
| パスワードや API キーを保管して、定期的に入れ替えたい | Secrets Manager | 秘密情報の保管と、自動ローテーション |
| 設定値や、軽い秘密情報を保管したい | Systems Manager パラメータストア | 安く手軽に保管。SecureString は KMS で暗号化 |
| 通信の TLS 証明書を使いたい | ACM | 証明書の発行と、自動更新 |

### 2. KMS（鍵の管理）

KMS は、暗号鍵を作って、使わせる権限を管理する。鍵そのものは外に取り出せない（対称鍵の場合）。

鍵の種類は、AWS が管理するもの（AWS マネージドキー）と、自分で作って設定するもの（カスタマーマネージドキー）。後者は、キーポリシーで誰が使えるかを決め、ローテーションの設定や無効化、削除の待機期間も自分で決める。

KMS の許可は、キーポリシーと IAM の両方が必要になる。別のアカウントから使うなら、キーポリシーでそのアカウントを許し、呼び出し側の IAM でも許可する。どちらか一方だけでは使えない。

S3、EBS、RDS などの暗号化は、裏で KMS を使う。エンベロープ暗号化で、データは KMS が発行したデータキーで暗号化される。

### 3. CloudHSM（専用の HSM）

CloudHSM は、自分専用の HSM（ハードウェアセキュリティモジュール）を VPC の中に置く。鍵の作成や利用は、利用者が管理する HSM のユーザーで行う。AWS の運用者も、鍵の中身は見られない。

KMS は AWS が管理する共有の HSM を使う。CloudHSM は、占有で鍵を管理したいとき、または規制で専用の HSM（FIPS 140-2 レベル3 など）が要るときに選ぶ。

### 4. Secrets Manager（秘密情報の保管と入れ替え）

Secrets Manager は、データベースのパスワードや API キーを保管する。アプリは API で取り出す。ソースにパスワードを書かずに済む。

最大の特徴は**自動ローテーション**。RDS などのデータベースは、Secrets Manager がパスワードを定期的に変えて、アプリ側は変更を意識せずに使い続けられる。料金は秘密情報の数と、API の呼び出し回数で決まる。

Systems Manager のパラメータストアも秘密情報を保管できるが、標準では自動ローテーションがない。「定期的に入れ替える」が要件なら Secrets Manager、「設定値を安く保管する」ならパラメータストア。

### 5. ACM（証明書）

ACM は TLS 証明書を発行し、ELB、CloudFront、API Gateway で使う。ACM が発行した公開証明書は、更新も自動で行われる。ただし、証明書の秘密鍵は取り出せない。EC2 に直接インストールしたいなら、取り出せる証明書が要る（ACM プライベート CA、または外部の証明書）。

### 6. 保存時と通信時の暗号化

S3 のバケットでは、SSE-S3（AWS が鍵を管理）、SSE-KMS（KMS の鍵を使う）、SSE-C（利用者が鍵を渡す）から選ぶ。
通信は TLS で守る。バケットポリシーで `aws:SecureTransport` の条件を使うと、暗号化されていない通信を拒否できる。

## 具体例・コード

社内の業務データベースを守る構成の例。

1. データベースの暗号化は、カスタマーマネージドの KMS キーで行う
2. 接続用のパスワードは Secrets Manager に置いて、30日ごとに自動で変える
3. 外部に公開する Web の証明書は ACM で発行し、ロードバランサに付ける
4. 規制で「専用の HSM で鍵を持つこと」が必要になったら、KMS のカスタムキーストアを CloudHSM に置く

## つまずきポイント

- KMS の鍵の中身を、取り出して別の場所で使えると思う。対称鍵は取り出せない。
- 別アカウントの KMS を使うのに、キーポリシーだけ書けば済むと思う。呼び出し側の IAM も要る。
- Secrets Manager とパラメータストアを、同じ機能だと思う。ローテーションの有無が違う。
- ACM の証明書を EC2 にそのままインストールできると思う。公開証明書は秘密鍵を取り出せないので、ELB などに付けて使う。
- CloudHSM を使えば、AWS の運用者から完全に守れると思う。鍵は利用者が管理するが、HSM 自体の保守や運用の責任の範囲も含めて確かめる。
