# マルチアカウントのガバナンス

## ひとことで

アカウントを分けて境界を作り、その上に許可の上限と監査を重ねるのが AWS のガバナンスになる。

## なぜ効くか / どこで使うか

1つのアカウントに全部載せると、権限も請求も障害範囲も混ざる。分けると、今度は「誰が何をできるか」を全体で揃える必要が出てくる。

SCP、Control Tower、IAM Identity Center は、その揃えるための道具になる。

## 本体の解説

境界はアカウント、統制は OU の継承でそろえる。

![[assets/web/aws-multi-account.svg]]

### 1. アカウントを分ける理由

分ける理由は主に4つある。権限の境界を作る、障害や事故の影響範囲を閉じ込める、請求を部署やシステムごとに分ける、規制や監査の対象範囲を区切る、の4つになる。

分けたうえで、共通のログ置き場やネットワークを持たせたくなるので、ガバナンスの道具が要る。

### 2. Organizations と SCP

Organizations でアカウントを束ね、OU（組織単位）で階層を作る。

SCP（サービスコントロールポリシー）は、メンバーアカウントの IAM ユーザーとロール（ルートユーザーも含む）ができる操作の上限を決める。SCP 自体は何も許可しない。実際に使える権限は、IAM で許可され、かつ SCP でも上限内にあるものだけになる。

効かない範囲も覚えておく。管理アカウントには適用されず、サービスリンクロールにも効かない。また、SCP が縛るのは自分の組織のプリンシパルだけなので、組織外のアカウントがリソースベースのポリシー（S3 のバケットポリシーなど）で許可されてアクセスしてくる場合は止められない。リソース側から上限をかけるのは、リソースコントロールポリシー（RCP）の役割になる。

### 3. Control Tower

Control Tower は、マルチアカウントの初期構成（Landing Zone）を作り、決めたルールを保ち続ける仕組みになる。

ルール（コントロール。以前はガードレールと呼んでいた）には3種類ある。違反する操作をそもそも止める予防的コントロール（SCP や RCP で実装）、違反を見つけて知らせる検出的コントロール（AWS Config で実装）、リソースを作る前に CloudFormation のテンプレートを検査するプロアクティブコントロールになる。アカウントの発行は Account Factory で行い、作るたびに同じ設定が当たる。

「新しいアカウントを同じ設定で量産したい」「設定の逸脱を検出したい」が出たら Control Tower を疑う。

### 4. IAM Identity Center

人が複数アカウントに入るときの入口になる。外部の IdP と連携し、権限セットをアカウントに割り当てる。

IAM ユーザーをアカウントごとに作る運用は、人の異動や退職で破綻する。Identity Center に寄せておけば、IdP 側でユーザーを無効にするだけで、全アカウントへのアクセスがまとめて止まる。

### 5. 監査と共有

ログは中央のアカウントに集める。CloudTrail の組織トレイル、Config のアグリゲータ、GuardDuty の委任管理が定番になる。

リソースの共有は RAM を使う。VPC サブネット、Transit Gateway、Resolver のルール、ライセンスなどを、アカウントをまたいで共有できる。

## 具体例・コード

新しいアカウントを1つ足すときの流れ。

1. OU を決める（本番、検証、サンドボックスなど）
2. Control Tower の Account Factory でアカウントを作る
3. その OU に継承される SCP を確認する
4. Identity Center で、必要な人のグループに権限セットを割り当てる
5. ログの集約先に、そのアカウントの証跡が届くことを確認する

## つまずきポイント

- SCP で何かを許可できると思う。SCP は上限を下げるだけで、許可はしない。
- 管理アカウントにも SCP が効くと思う。効かない。
- SCP で、組織外からリソースベースのポリシー経由で来るアクセスを止められると思う。止められないので RCP を使う。
- IAM ユーザーをアカウントごとに作り続ける。退職時の漏れが起きる。
- ログを各アカウントに置いたままにする。改ざんや削除ができてしまい、監査にならない。
