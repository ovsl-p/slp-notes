# Rust のメモリ管理

## ひとことで

Rust は GC を使わずにメモリ安全を達成する。代わりに **所有権 (ownership)** と **借用 (borrow)** というコンパイル時の規則で、次の3点を型検査で強制する。

1. すべての値には所有者がちょうど1ついる。
2. 所有者がスコープを抜けた瞬間に値は解放される（RAII / `Drop`）。
3. 参照は所有者より長生きできない（借用規則 + ライフタイム）。

GC の停止も参照カウントの常時加減算もないので、実行時コストはほぼゼロ。解放漏れ・二重解放・use-after-free・データ競合が「実行時のバグ」ではなく「コンパイルエラー」になるのが本質的な違い。

## なぜ効くか / どこで使うか

- 予測可能な遅延: GC の stop-the-world がない。音声処理・ゲーム・組み込み・リアルタイム系で効く。
- 解放タイミングが決定的: スコープ終了 = 即解放。ファイル/ロック/バッファを `Drop` に載せれば後始末を忘れられない。
- データ競合が型で防がれる: `&mut` は同時に1つだけ、という規則がスレッドをまたいでも（`Send`/`Sync` 経由で）効く。
- 弱点: 参照グラフ（双方向リスト、ツリーの親ポインタ、GUI、一般のグラフ）は所有権モデルと相性が悪い。`Rc<RefCell<T>>`、インデックス、arena で迂回する必要がある。→「つまずきポイント」

## 前提となる知識

これを知らないと、エラーメッセージの意味が分からないまま写経することになる。

| 知っておくこと | なぜ Rust で必要か |
| --- | --- |
| スタックとヒープ | サイズがコンパイル時に決まる値はスタック、可変長はヒープ。Rust の「ムーブ」は多くの場合スタック上のビットコピーに過ぎない |
| ポインタと参照 | `&T` はアドレス（1ワード程度）。`String` は (ptr, len, cap) の3ワードと理解すると図が描ける |
| RAII / デストラクタ | `Drop` はまさにこれ。「スコープを抜けたら後始末」だけ押さえれば足りる |
| 値セマンティクス vs 参照セマンティクス | Rust のデフォルトは値。代入や引数渡しはコピーではなく **ムーブ** になる。Java/Python の参照の感覚で書くと最初に必ず詰まる |
| ジェネリクスとトレイト | `Copy` / `Clone` / `Deref` / `Drop` / `Send` / `Sync` / `Borrow` がメモリまわりの挙動を決める |
| クロージャとキャプチャ | 環境を「借用」するか「ムーブ」するかが推論される（`Fn` / `FnMut` / `FnOnce`）。ここで借用エラーが出やすい |
| 並行性の基礎 | データ競合とは何か、なぜ `Mutex` が要るか。`Send` / `Sync` を知らないとスレッド版で必ず詰まる |
| アロケータとキャッシュ | アロケーション回数がそのまま性能に効く。リアルタイム音声スレッドでは途中の `malloc` を避ける、など |

推奨学習順: The Book の **ch.4（所有権）→ ch.10（ジェネリクス・トレイト・ライフタイム）→ ch.15（スマートポインタ）**。GC 言語の出身でも ch.4 は飛ばさない。

## 本体の解説

### 0. まずはイメージから（噛み砕いた説明）

規則を覚える前に、**「モノの持ち主」と「貸し借り」**の絵を持っておくと全部つながる。

#### たとえ話

- 値（`String` など）は **ノート1冊**。
- 変数は **そのノートを持っている人**。
- ノートの持ち主は **常に1人だけ**。手渡したら、渡した側はもう持っていない。
- 「中身を見せて」と頼むのが **借用（`&T`）**。読むだけなら何人に同時に見せてもいい。
- 「書き換えるから独占させて」が **可変借用（`&mut T`）**。書いている間は誰にも見せられない。
- ノートの持ち主が帰っちゃったら、借りてた人も読めなくなる。これが **ライフタイム**。

| Rust の用語 | 日常語にすると |
| --- | --- |
| 所有権 (ownership) | そのノートの持ち主であること |
| ムーブ | ノートを相手に手渡す（自分は空手になる） |
| `clone()` | ノートをコピーして2冊にする（コピー代がかかる） |
| 借用 `&T` | 「読むだけ」で貸してもらう |
| 可変借用 `&mut T` | 「書き込むから独占」で貸してもらう |
| ライフタイム | 貸してもらえるのは持ち主がいる間だけ |
| `drop` | 持ち主が帰る＝ノートを処分する |

#### 15行で全体像

```rust
fn main() {
    let s = String::from("hello");   // s はノートの持ち主
    let t = s;                       // 手渡した。所有者は t に移った（ムーブ）
    // println!("{s}");              // error[E0382] s はもう持ち主じゃない

    let n = t.len();                 // 借りて読むだけ（&t が自動で作られる）
    println!("{t} は {n} 文字");      // t はまだ持ち主なので使える
}                                    // ここで t が処分される（drop）
```

これだけで「所有権の3規則」が全部出てくる。**代入はコピーじゃなく手渡し**、というのが Java / Python 出身者が最初に裏切られるポイント。

「なぜ手渡しにするのか」は、コピーしたつもりで2人が同じノートを持ち、片方が処分したあと片方が読み続ける事故（**二重解放 / use-after-free**）を型で禁止したいから。コピーが欲しいときは `clone()` と明示させる。

#### 借用は「別名 XOR 可変性」

- 読むだけ（`&T`）… 同時に何個でもOK
- 書き換え（`&mut T`）… 同時に1つだけ。その間は `&` も禁止

```rust
let mut v = vec![1, 2, 3];
let a = &v;          // 読みの借用
let b = &v;          // もう1個OK
println!("{a:?} {b:?}");
// let c = &mut v;   // error[E0502] まだ読んでる人がいる間は書き込みダメ
```

```rust
let mut v = vec![1, 2, 3];
{
    let c = &mut v;  // 書き込みの借用は1つだけ
    c.push(4);
}                    // ここで借用が終わる
println!("{v:?}");   // もう自由
```

**コンパイラの見方**: 「今この瞬間、読んでる人がいるか？」「書き込んでる人がいるか？」を1行ずつ追いかけているだけ。エラーが出たら「どの行とどの行で重なってるか」を探す。エラーメッセージの `first borrow occurs here` / `second borrow occurs here` がその2行を指している。

#### なぜこんな規則が要るのか

禁止したい事故は2種類だけ。

1. **参照が消えたメモリを触る**（dangling pointer / use-after-free）
   → 「参照は参照先より長生きできない」で禁止（ライフタイム）。
2. **2人が同時に同じ場所を書き換える**（データ競合）
   → 「`&mut` は同時に1つだけ」で禁止。この規則はスレッドをまたいでも効くので、`Mutex` すら「実行時に守らせる」保険になる。

GC 言語はこの2つを実行時の仕組みで防いでいる。Rust は**コンパイル時にタダで**防いでいる、というのが違い。

#### つまずいたときの処方箋（この順に試す）

1. **借用を短くする**（`let` のスコープを `{}` で狭める、1文で終わらせる）
2. **所有をやめる**（引数は `&str` / `&[T]` で受ける）
3. **所有を移す**（`String` を返す、`move` を付ける）
4. **共有する**（`Rc` / `Arc`、変更も要るなら `RefCell` / `Mutex`）
5. 最後の手段で `clone()`（動くが意図と性能を捨てている）

学習中は 5 から入ってもいい。**とりあえず動かして、あとで 1〜4 に直す**ほうが、最初から完璧を狙うより早く身につく。

### 1. 所有権の3規則

- 各値には「所有者」が1つだけいる。
- 所有者は同時に1つ。代入・引数渡し・`return` で所有者が移る（**ムーブ**）。
- 所有者がスコープを抜けると値は `drop` される。

```rust
fn consume(s: String) -> usize {
    s.len()
} // ← ここで s が drop され、ヒープの "hello" は解放される

fn main() {
    let s = String::from("hello");
    let n = consume(s);        // 所有権が consume へムーブ
    // println!("{s}");        // error[E0382]: borrow of moved value: `s`
    println!("{n}");
}
```

### 2. ムーブ / Copy / Clone

- ムーブはスタック上の値（ポインタ・長さ・容量）の浅いコピー。ヒープの中身はコピーされず、**解放責任だけが移る**。だから二重解放が起きない。
- `Copy` な型（`i32`、`f64`、`bool`、`char`、`&T`、`[T; N]` など）はムーブではなくコピー扱いになり、元の変数も使える。
- `Copy` でない型を明示的に複製したいときは `.clone()`（ヒープも複製する。コストがあるので「借りチェッカを通すためだけの clone」は最後の手段）。

```rust
let a: i32 = 1;
let b = a;        // Copy なのでコピー。a もまだ使える
println!("{a} {b}");

let s1 = String::from("hi");
let s2 = s1.clone();   // ヒープも複製。s1 と s2 は別物
println!("{s1} {s2}");
```

### 3. 借用と借用規則

参照を取ることを **借用 (borrow)** と呼ぶ。規則は「別名 XOR 可変性」の一言に尽きる。

- 不変借用 `&T` は同時に何個でもよい。
- 可変借用 `&mut T` は同時に1つだけ。
- `&mut` が生きている間は、`&` すら取れない。

さらに「参照は参照先より長生きできない」がライフタイムで検査される。

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    for x in &v {          // v を不変借用（ループ全体で生きている）
        v.push(*x);        // error[E0502]: cannot borrow `v` as mutable
                           // because it is also borrowed as immutable
    }
}
```

回避策は「借用が重ならない形に書き換える」こと。`clone()` で逃げる前に、まずこれを試す。

```rust
let mut v = vec![1, 2, 3];
let n = v.len();
for i in 0..n {
    let x = v[i];   // 読み取りはこの文で完結
    v.push(x);
}
```

（`v.push(v[i])` も two-phase borrow のおかげで通るが、説明上は分けたほうが見通しがよい。）

### 4. ライフタイム

ライフタイムは「参照の有効期間」。ふだんは省略規則（elision）で書かなくて済む。

- 引数が1つだけの参照 → 戻り値はその参照のライフタイム。
- `&self` / `&mut self` があるメソッド → 戻り値は self のライフタイム。
- 引数の参照が複数で戻り値が参照 → **注釈が必要**。

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
// 「戻り値は x と y の短いほうと同じ期間だけ有効」という意味
```

`'a` は期間を延ばす魔法ではなく、「この範囲なら安全」という制約の宣言。所有権を移す（`String` を返す）ほうが素直な場面も多い。

### 5. スコープ終了 = 解放（Drop / RAII）

```rust
struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) { println!("drop {}", self.0); }
}

fn main() {
    let _a = Noisy("a");
    let _b = Noisy("b");
} // drop b → drop a（宣言の逆順）
```

- `Drop` の実装は「スコープ末尾に自動挿入されるクリーンアップ」。
- 早期 return や `?` による中断でも必ず走る。ロック解放・一時ファイル削除・バッファ返却をここに置く。
- 明示的に早く解放したいときは `drop(x)`。

### 6. ヒープを持つ型とスマートポインタ

| 型 | 何をしてくれるか | 使う場面 |
| --- | --- | --- |
| `Box<T>` | ヒープに置く。サイズはポインタ1つ分 | 再帰型、大きな値、`dyn Trait` |
| `Rc<T>` | 参照カウント（単一スレッド）。複数の所有者 | 共有される読み取り専用データ |
| `Arc<T>` | 原子的参照カウント（スレッド間） | スレッドに共有するデータ |
| `Cell<T>` / `RefCell<T>` | 内部可変性（`&self` から中身を変更） | `Rc` と組み合わせた共有 + 変更 |
| `Mutex<T>` / `RwLock<T>` | 実行時のロックで排他 | `Arc` と組み合わせた共有 + 変更（スレッド） |
| `Vec<T>` / `String` | 所有版（ヒープ確保を伴う） | 所有が本当に必要なときだけ |

`Box` は「ムーブを軽くする」ためにも使う。大きな構造体を値で持ち回るとムーブがコピーになるが、`Box` にすればポインタ1つ分の移動で済む。

### 7. 内部可変性（interior mutability）

借用規則はコンパイル時検査なので、`&self` から中身を書き換えたい（キャッシュ、カウンタ、グラフ）ときには原理的に通らない。そこで `Cell` / `RefCell`（実行時検査。違反すると panic）や `Mutex`（ロック）を使う。

```rust
use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let shared = Rc::new(RefCell::new(vec![1, 2]));
    let a = Rc::clone(&shared);        // 所有者を増やす（中身は複製しない）
    a.borrow_mut().push(3);
    println!("{:?} / {} refs", shared.borrow(), Rc::strong_count(&shared));
}
// 注意: 同じ式の中で borrow() と borrow_mut() を同時に呼ぶと panic する
// （{:?} の表示中も借用は生きている）
```

`Rc` は循環参照をリークする（お互いを参照し合うとカウントが0にならない）。親を参照したいときは `Weak` を使う。

### 8. スレッドと Send / Sync

- `Send`: 所有権をスレッドへ移せる型。
- `Sync`: `&T` を複数スレッドから共有してよい型。
- `Rc` / `RefCell` はどちらも `!Send` / `!Sync`。スレッドに渡すなら `Arc` + `Mutex`（または `Arc` + 原子的型）。

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];
    for _ in 0..4 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *c.lock().unwrap() += 1;
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", *counter.lock().unwrap());   // 4000
}
```

### 9. 実務での型の選び方（アロケーションを減らす）

- 引数は所有型ではなく **借用** で受ける。`String` ではなく `&str`、`Vec<T>` ではなく `&[T]`。

```rust
fn count_words(text: &str) -> usize { text.split_whitespace().count() }

let owned = String::from("a b c");
count_words(&owned);        // &String は Deref 強制で &str になる
count_words("a b c");
```

- 戻り値で所有が必要かを考える。借用で返せるならライフタイムを1つ書くだけ。
- ループ内で `String` を作る・`format!` を積むのは避ける（リアルタイム処理では特に）。

## 具体例・コード

借用エラーの典型と、その対処の対応表。

| エラー | 意味 | 対処 |
| --- | --- | --- |
| `E0382 borrow of moved value` | ムーブ済みの値を使った | 借用で渡す / `clone()` / `Rc` で共有 |
| `E0502 cannot borrow as mutable` | 不変借用が生きている間に可変借用 | 借用のスコープを短くする、一度 `collect()` する |
| `E0499 cannot borrow as mutable more than once` | 可変借用が2つ | 分割（`split_at_mut`）やインデックス経由に |
| `E0597` / missing lifetime specifier | 参照が参照先より長生きする | 所有型を返す、`'a` を書く、借用の範囲を狭める |
| `E0277 Rc<...> cannot be sent between threads` | `!Send` な型をスレッドへ | `Arc` + `Mutex` に置き換える |

実務での型の選び方（迷ったときの優先順）:

1. 借用で済むか（`&T` / `&str` / `&[T]`）→ 済むなら借用。アロケーションゼロ。
2. 所有が要るか（`String` / `Vec<T>`）→ 値を保持・返すなら所有。
3. 共有が要るか → 単一スレッドなら `Rc`、スレッド跨ぎなら `Arc`。
4. 共有しつつ変更するか → `RefCell`（単一スレッド）/ `Mutex`（スレッド）。

## つまずきポイント

- **for ループ中の変更**: イテレータが `v` を借用している間は `v.push()` できない。先に `collect()` するか、インデックスループにする。
- **クロージャが環境を握り続ける**: `FnMut` で環境を可変借用したクロージャを、同じ変数を触る別のコードと同時に使うとエラー。`move` で所有させるか、スコープを閉じる。
- **構造体に参照を持たせる**: `struct Foo<'a> { s: &'a str }` は可能だが、ライフタイムが呼び出し側に漏れる。迷ったら `String` で所有する（`'static` が楽）。
- **`&String` と `&str`**: ほぼ常に `&str` で受ける。`&String` を要求する API は設計ミスのことが多い。
- **部分ムーブ**: 構造体のフィールドを1つムーブすると、その構造体全体はもう使えない。`Option::take` や `std::mem::take` / `replace` で回避。
- **`clone()` で借りチェッカを通す**: 動くが意図と性能を捨てている。まず借用の範囲を見直す。
- **`RefCell` の panic**: `already borrowed: BorrowMutError` は「実行時の借用規則違反」。同じ式の中で `borrow()` と `borrow_mut()` を混ぜていないか確認。
- **`Rc` の循環参照**: リークする（メモリは解放されない）。親参照は `Weak` に。
- **async と参照**: `Future` はしばしば `'static` を要求するので、`async` ブロックへ参照を渡すとライフタイムエラーが出やすい。所有させるか `Arc` を使う。自己参照は `Pin` の領域。
- **デッドロック**: `Arc<Mutex<T>>` で同じ Mutex を再帰的にロックしない。ロックのスコープを1文に閉じる。
